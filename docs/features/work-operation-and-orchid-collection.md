# 작업 실행과 난 그룹 정책

## 1. 결정 상태

`2026-07-20` 기준 결정이다. 운영 작업과 난 묶음 이력은 `WorkOperation`으로 통일한다. 기존 `WorkRecord` 행은 마이그레이션 원본과 감사 목적으로 보존하지만 신규 이동·입고·사용자 작업을 기록하거나 난 묶음 이력 API에 노출하지 않는다.

동 전체·자동 그룹·사용자 그룹·직접 다중 선택 기간 작업, 월간 캘린더, 작업 상태와 그룹 관리를 구현했다. 대상 새로고침은 후속 단계다.
작업 API와 이력 조회는 항상 `WorkOperation` 계약을 사용한다. 기존 수동 작업 기록 API와 기능 플래그 기반 복귀 경로는 제거했다.

작업 관리 화면은 `작업 목록`, `캘린더`, `작업 이력` 탭으로 나눈다. 신규 작업 등록과 진행 관리는 작업 목록에서, 월간 일정 관리는 캘린더에서 처리한다. 작업 목록은 계획·진행 중·일시중지 작업과 농장 기준 오늘 상태가 변경된 작업만 기본 표시한다. 완료·취소·보정된 `WorkOperation`은 작업 이력에서 확인한다.

작업 상세의 `관계 그래프` 탭은 별도 단계 선택 없이 `투입 난 묶음·입고 → 적용 작업 → 잔류·결과
난 묶음 → 연계 작업` 흐름을 한 번에 표시한다. 난 묶음 노드는 작업 시점의 수량·상태·위치 snapshot을
사용하고, 작업 후 달라진 주요 값도 함께 표시한다. Mutation과 revision은 사용자 화면에 노출하지 않는다.
자리 이동 뒤 원래 자리에 남아 연계 폐기되는 SOURCE 상태는 사용자 관점의 `잔류`로 표현한다.
자리 이동·분갈이·분주·합식에서 전량 투입되어 `종료`된 원본은 폐기 결과가 아니므로 관계 그래프의
결과 노드로 반복 표시하지 않고 투입 노드와 새 결과 묶음만 표시한다. 실제 `DISCARD` 효과만 폐기
흐름으로 표현한다.
무효화된 작업은 무효화 보상 Mutation을 그래프에 추가하지 않고 무효화 직전의 정상 작업 효과 흐름으로
구조를 고정한다. 해당 작업으로 들어가는 `투입`·`입고` 간선에는 `무효화됨`을 표시하고, 작업 노드부터
당시 결과 묶음·후속 작업·간선을 흐리게 표시한다. 투입 원본과 영향을 받지 않은 다른 가지는 일반 명암을
유지한다.
같은 `WorkCommandReceipt`에서 생성된 형제 작업은 등록 요청만 공유할 뿐 작업 간 실행 관계가 아니므로
그래프에 표시하지 않고, 작업 목록의 `함께 등록` 배지와 관계 카드에서만 탐색한다. 날짜·제목·품종·대상
유사성으로 관계를 추론하지 않는다. `sourceScopeType`은 대상 선택 출처이며 작업 생성 출처로 사용하지
않는다.

개발용 Mutation 테스트 화면은 작업 ID를 기준으로 작업·Mutation·revision·계보를 함께 조회하는 기술
그래프를 제공한다. `WORK`, `MUTATION`, `LINEAGE` 단계와 계보 깊이를 전환해 작업 효과와 내부 Mutation
연결을 점검한다.

Receipt의 `resultOperationIds`는 동일 생성 요청 판정의 기준으로 유지한다. 작업에서 Receipt를 찾는
membership은 목록 관계 카드의 역방향 조회용 복제이며, migration도 존재하는 Receipt 결과만 옮기고
과거 작업의 관계를 휴리스틱으로 보충하지 않는다.

작업 목록과 캘린더는 대상 없는 작업 요약과 집계 진행률만 조회한다. 목록의 생성 묶음과 선후 연계 여부는 배지로 표시하고, 배지를 선택한 경우에만 목록 아래 관계 카드에 해당 작업들을 조회한다. 생성 출처는 목록 배지로 표시하지 않는다. 작업 목록과 작업 이력에서 작업을 선택하면 단건 상세를 조회해 작업 유형별 입력 내용, 작업자, 메모와 대상별 실행 현황을 함께 표시한다. 농약 작업은 약제명·희석 배수·사용량을 작업 상세에서 확인한다.

작업 유형 API는 등록 가능 모드, 전용 워크플로, 대상 종류, 설정 수정 가능 여부를 함께 제공한다. 프론트는 작업 코드 조합으로 이 규칙을 재정의하지 않는다. 사용자 정의 작업 유형은 서버가 허용한 기록형 템플릿만 생성·수정할 수 있다. 작업 대상 응답은 후속 회차가 참조할 결과 난 묶음 ID를 정형 필드로 제공하며, 프론트는 `resultDetails` JSON을 직접 파싱하지 않는다.

작업과 각 대상 응답은 서버가 판정한 `availableActions`를 함께 제공한다. 전체 작업 action은 상태와 대상 종료 여부를, 대상 action은 전용 workflow와 남은 수량을 함께 반영한다. 프론트는 이 action을 버튼·dialog에 매핑하고 업무 가능 여부를 다시 계산하지 않는다.

묶음 관리 화면의 단일·다중 선택 작업 추가도 작업 관리 화면과 동일한 작업 등록 모달을 사용한다. 이 경로에서는 선택한 난 묶음 ID를 `MANUAL_SELECTION` 대상으로 고정하고, 대상 변경 없이 작업 기록 또는 계획을 등록한다.

자리 이동은 품종별 작업으로 분리한다. 모든 원본과 결과가 명시적인 1:1이고 각 원본 전량의 위치만 바뀌면 기존 난 묶음 ID를 유지하고 하나의 일괄 이동 Mutation으로 기록한다. 그 외에는 한 개 이상의 원본 난 묶음 선별 수량을 실행 회차에서 합친 뒤 한 개 이상의 결과 난 묶음으로 나눈다. N:M 흐름에는 결과별 직접 원본 수량 배분을 만들지 않는다. 상태가 좋은 수량을 먼저 이동하고 원래 자리에 남은 총 폐기 수량은 원본별 선별 수량에 비례해 자동 배분한 뒤, 같은 트랜잭션에서 별도의 완료된 폐기 작업으로 기록한다.

자리 이동·분갈이·분주·합식의 일부 실행에서는 작업 수량 비율을 기준으로 원본 난 묶음 배치의 뒤쪽 구간을 자동 제안한다. 배치 선택기는 원본 난 묶음 위치를 별도 색상으로 표시한다. 사용자는 실제로 비운 뒤쪽 칸을 수정할 수 있고, 선택한 구간만큼 원본 배치가 앞쪽으로 줄어든 뒤 결과 난 묶음 배치에 재사용된다.

분갈이·분주·합식 결과 난 묶음은 작업 전 원본 상태를 이어받는다. 원본 수량을 모두 사용해 원본이 `종료`되더라도 일반 결과가 `종료` 상태를 상속하지 않는다. 분주 후보와 별도 보관 결과만 각각 `분주 예정`, `별도 보관` 상태를 사용한다.

## 2. 대상 확정

- 그룹과 상위 범위는 대상 선택 조건이다.
- 저장 시 활성 난 묶음과 수량이 1 이상인 난 묶음을 실제 대상으로 확정한다.
- 종료, 폐기, 판매 완료 상태는 제외한다.
- 작업 시작 전 새로고침은 후속 단계에서 제공한다.
- 작업 시작 후 대상은 자동 변경하지 않는다.
- 작업 당시 품종, 년생, 화분 표시값, 수량, 위치를 스냅샷으로 보존한다.
- 자동 그룹은 그룹 키, 사용자 그룹은 그룹 ID, 직접 선택은 난 묶음 ID 목록을 조건 스냅샷으로 함께 보존한다.
- 포트 작업 계획은 선택한 입고 기록을 잠근 상태에서 활성 계획 중복을 한 번에 확인한다. 품종별 배치 계획도 전체 선택 대상을 같은 트랜잭션에서 확정한다.
- 작업 관리의 포트 작업 기록과 입고 관리의 즉시 실행은 `inbound-potting-records` 계약을 함께 사용한다. 실행별 멱등 키로 기존 효과를 반환하며, 활성 포트 작업 계획이 있으면 새 작업을 만들지 않고 해당 대상을 완료한다.

## 3. 자동·사용자 그룹

- 자동 그룹 기준은 `variety_id + 현재 년생 + pot_size_code`다.
- 자동 그룹은 영속 엔티티를 만들지 않고 조회 시 계산한다.
- 화분 크기 코드는 `POT_2`, `POT_2_5`, `POT_3`, `POT_3_5`, `POT_4`, `POT_4_5`, `POT_5`, `POT_6`, `HANGING`, `ETC`를 사용한다.
- 미지정은 `UNSPECIFIED`, 기존 값 중 안전하게 매핑할 수 없는 값은 `UNMAPPED`로 보존하고 자동 그룹에서 제외한다.
- `UNMAPPED` 검수 목록은 `scripts/data-audit/unmapped-pot-sizes.sql`로 조회한다.
- 자동 그룹은 조회 시 계산하며 수량 0, 종료·폐기·판매 완료, `UNMAPPED` 난 묶음을 제외한다.
- 자동 그룹 키는 조회 조건이며 난 묶음 속성이 변경되면 자동으로 새 그룹 결과에 반영된다.
- 사용자 그룹 소속은 위치와 속성이 바뀌어도 유지한다.
- 하나의 난 묶음은 여러 사용자 그룹에 속할 수 있고, 사용자가 해제하기 전까지 소속 이력을 보존한다.
- 사용자 그룹은 삭제하지 않고 보관하며, 보관된 그룹의 소속은 변경하지 않는다.
- 구조 변경 결과 난 묶음은 사용자 그룹을 기본 상속하지 않는다. 완료 시 사용자가 선택한다.

## 4. 상태와 전파

- 전체 상태: `PLANNED`, `IN_PROGRESS`, `PAUSED`, `COMPLETED`, `CANCELED`, `CORRECTED`, `VOIDED`.
- 대상 상태: `PENDING`, `IN_PROGRESS`, `COMPLETED`, `SKIPPED`, `CANCELED`, `FAILED`.
- 전체 작업은 `PLANNED → IN_PROGRESS ↔ PAUSED → COMPLETED` 흐름을 제공한다.
- 대상은 `PENDING → IN_PROGRESS → COMPLETED` 또는 `SKIPPED`로 처리한다.
- 모든 대상이 완료 또는 건너뜀 상태가 되면 전체 작업은 마지막 실행 완료일 기준으로 자동 완료된다.
- 일부 대상만 완료된 전체 작업 취소는 완료된 대상과 효과를 유지하고, 미완료 대상만 취소 상태로 닫는다.
- 모든 대상이 닫힌 진행률 100% 작업은 일시중지, 추가 실행 등록, 취소 대상이 아니다.
- 상위 작업을 난 묶음별 작업 행으로 복제하지 않는다. `WorkOperationTarget` 연결로 조회한다.
- 조회 중복 기준은 `workOperationId + orchidGroupId`다.

## 5. 구조 변경과 수량

- 사용자 정의 작업 유형은 기록형만 허용한다.
- 난 묶음 생성·종료·수량·위치 변경은 시스템 작업 유형만 수행한다.
- 분갈이 전 원본 수량은 `투입 수량 + 원본 잔여 수량`이다. 결과가 투입보다 적으면 차이를 손실로, 많으면 촉 분리에 따른 증식으로 자동 기록한다.
- 자리 이동은 전체 이동 결과 수량이 전체 선별 수량 이하여야 한다. 원본과 결과가 명시적인 1:1 전량 이동이면 난 묶음 ID와 수량·속성을 유지하고 위치만 변경하며 별도 계보를 만들지 않는다. 그 외 이동 결과는 `MOVED_TO` 실행 회차 계보에 연결하고, 원래 자리에 남은 차이는 원본별 선별 수량 비율로 배분하여 `MOVEMENT_DISCARD`로 연결된 별도 폐기 작업에서 차감한다. 정수 나머지는 최대 나머지 방식으로 배분하며 동률은 난 묶음 ID 오름차순으로 해소한다.
- 결과 난 묶음은 원본을 덮어쓰지 않고 저장된 실행 회차를 사이에 둔 계보로 연결한다.
- 완료된 구조 변경 작업은 삭제하거나 일반 취소하지 않고 보정 작업을 연결한다.
- 보정 관계는 원본 작업과 별도 `CORRECTION` 작업, 사유를 보존하고 원본을 `CORRECTED` 상태로 표시한다.
- 보정 효과는 원본 작업의 작업일과 원본 작업이 만든 결과의 수량·상태를 변경하고 전후 값을 감사 상세로 보존한다.
- 후속 작업·이동·판매·입고 연결과 예약 수량을 침해하는 보정은 허용하지 않는다.
- 새 결과 생성이나 기존 계보 교체는 현재 보정 효과 범위에 포함하지 않는다.
- 현실에서 수행하지 않았는데 완료로 잘못 등록한 구조 변경(자리 이동·분갈이·분주·합식 포함)과 독립 폐기는 `VOIDED`로 무효화한다. 원본 작업과
  Mutation은 삭제하지 않고 `COMPENSATION` Mutation을 추가하며 revision은 계속 증가한다.
- 구조 변경 무효화는 원본 Mutation의 모든 SOURCE와 RESULT에 상쇄되지 않은 후속 변경이 없고, 결과 난
  묶음에 다른 유효 작업·판매·입고 참조가 없을 때만 허용한다. 후속 구조 변경과 그 보상 Mutation은
  유효 이력에서 상쇄하므로 최신 작업부터 이전 작업 순서로 연속 무효화할 수 있다. 원본 상태 복원과
  모든 결과 생성 취소는 한 트랜잭션으로 처리한다.
- 자리 이동에 연관 폐기가 연결되어 있으면 이동과 폐기의 연속 Mutation을 한 번에 검사하고 하나의
  보상 Mutation으로 원래 상태를 복구한다. 연관 폐기 작업만 따로 무효화할 수 없으며 두 작업 이력은
  모두 `VOIDED`로 보존한다.
- 포트 작업은 생성 결과에 후속 Mutation, 다른 작업 또는 판매 참조가 없고 연결 입고가 배치 완료
  상태일 때만 무효화한다. 생성된 난 묶음은 삭제하지 않고 생성 취소 상태로 보존하며, 배치 완료 후
  수정이 금지된 기존 입고 기록은 값을 복원하지 않고 `POTTING_PENDING` 상태로 다시 연다. 취소된 생성
  결과는 활성 결과로 보지 않으므로 새 키로 포트 작업을 다시 실행할 수 있다.
- 입고 관리에서 배치 완료 유리병 모종을 취소하면 포트 작업을 먼저 무효화한 뒤 원본 입고 작업을
  취소한다. 즉시 배치 입고는 입고 생성 Mutation을 보상하고 연결 입고 작업을 `VOIDED`로 남긴다.
  여러 입고가 하나의 포트 작업에 포함된 경우 포트 작업 무효화는 형제 입고 결과에도 함께 적용된다.
- 같은 난 묶음의 Mutation이 하나의 연속 상태 체인을 이루지 않는 작업과 판매·입금처럼 외부 효과가
  있는 작업은 자동 무효화하지 않는다. 독립 폐기는 후속 변경이 없는 경우 수량·상태를 보상 Mutation으로
  복구할 수 있으며, 실제 현장 폐기를 되돌리는 용도가 아니라 잘못 등록한 기록을 바로잡는 용도로만 사용한다.
- 현장 실사로 확인한 현재 상태가 시스템과 다르면 `RECONCILIATION` 작업으로 수량·상태·위치를
  동기화한다. 동기화 전후 snapshot과 사유를 보존하고 과거 작업을 무효화한 것으로 취급하지 않는다.
- 현장 동기화는 예약 수량보다 작은 수량이나 다른 활성 난 묶음과 겹치는 배치를 허용하지 않는다.

## 6. 기존 이력

- 기존 `work_records`는 마이그레이션 원본과 감사 목적으로 보존하되 운영 이력 조회에는 사용하지 않는다.
- 자리 이동 선행 폐기로 저장된 기존 `WorkOperation`은 이동 후 잔여 폐기 상태 체인으로 이관한다. 당시 원본별 폐기 배분은 과거 사실로 보존하고, 관계는 `parentOperationId`와 `MOVEMENT_DISCARD`만 사용한다. 관계를 중복 표현하던 `details.movementOperationId`와 `details.relation`은 제거한다.
- 과거 `TRANSFORM`으로 저장된 자리 이동 중 원본·결과가 명시적인 1:1 전량 대응이고 위치 외 상태가 같은 이력은 기존 원본 ID를 유지하는 `MOVE` 체인으로 이관한다. 생성됐던 중간 결과 ID의 후속 Mutation·작업·판매 참조는 원본 ID로 연결하고, 제거된 ID와 보존 ID의 대응 및 제거 직전 snapshot은 `orchid_group_identity_migrations`에 감사 기록으로 남긴다. N:M 변환, 부분 수량, 속성 변경, 대응이 불명확한 이력은 변경하지 않는다.
- 과거 이동 실행기가 1:1 전량 이동 결과를 새로 만들면서 메모·입고 출처 같은 원본 전용 속성을 누락한 경우, 결과 생성 이후 후속 Mutation이 없는 이력에 한해 핵심 품종·수량·상태가 같음을 확인하고 원본 속성을 복원하여 `MOVE`로 이관한다.
- 사용자 수동 작업 입력은 즉시 완료 `WorkOperation`으로 저장한다.
- 신규 즉시 완료 작업의 대상 효과는 한 트랜잭션에서 모아 일괄 저장한다. 이미 존재하는 작업을 다시 실행하는 경로에서만 대상별 효과 키를 확인한다.
- 키가 있는 즉시 실행·구조 변경 기록·포트 기록은 요청 지문과 결과 작업 ID를 같은 트랜잭션에 저장한다. 같은 범위·키의 병렬 요청은 DB 접수 기록으로 직렬화하며 실패하면 접수 기록도 롤백한다. 재요청은 저장된 ID의 현재 상세를 반환하므로 최초 HTTP 응답의 시각 정밀도나 이후 변경 상태까지 고정하는 계약은 아니다.
- 즉시 실행 키는 작업 유형 전체에서 공유한다. 구조 변경 단건 기록은 별도 범위이며, 일괄 기록의 identity는 입력 순서의 실행 키 목록이다. 포트 단건은 입고 ID와 키, 일괄 포트 기록은 입력 순서의 입고 ID·키 목록으로 구분한다. 키 없는 계획·일반 기록 API에는 새 멱등성 보장을 추가하지 않는다.
- 요청 지문은 객체 키 순서와 숫자 표기를 정규화한다. 의미 있는 배열 순서·문자열·자유 JSON 내용은 보존하며 컬렉션 소속 ID 집합만 정렬한다. 같은 키로 내용을 바꾸면 HTTP 409 `IDEMPOTENCY_KEY_REUSED`를 반환한다.
- 작업 효과 identity는 종류와 무관한 `(workOperationId, effectKey)`이며 DB UNIQUE로 고정한다. 완료된 구조 변경 회차도 저장된 원문을 확인한 뒤 재조회한다. 포트 효과는 `POTTING:{inboundRecordId}:{idempotencyKey}`로 기록하고 기존 `POTTING:{idempotencyKey}` 이력도 조회한다.
- V25 이전 즉시 실행 키는 결과 ID만 이관한다. 원문이 없어 같은 요청인지 확인할 수 없는 재실행은 HTTP 409 `IDEMPOTENCY_REPLAY_UNAVAILABLE`로 거절하며 기존 작업 조회는 유지한다. 과거 상태를 현재 난 묶음에서 역산해 요청 지문을 만들지 않는다.
- 직접 자리 이동과 입고를 포함한 신규 시스템 작업도 `WorkOperation`으로 기록한다.
- 난 묶음 이력 API는 `WorkOperationTarget`과 `WorkEffectOrchidGroup` 연결만 조회한다.
- V8에서 변환된 기존 이력은 변환 결과인 `WorkOperation`을 통해 조회한다.
- Mutation Engine writer에서는 난 묶음 상태를 바꾸는 효과가 기존 effect key를 그대로 Mutation 원인 키로 사용한다. 효과 저장과 함께 `WorkAppliedEffect.mutationId`, `correlationId`를 기록하며 단일 원본 호환 계보에도 같은 Mutation ID를 연결한다.
- cutover 이전 상태 변경 Work 효과도 동일한 `(workOperationId, effectKey)` identity로 complete state-chain Mutation에 이관한다. `DISCARD`, `MOVE`, `DIVIDE`, `MOVEMENT`, `REPOT`, `POTTING`만 대상이며 난 묶음 관계는 연속 `CREATE/CHANGE/DELETE` Entry로 연결하고 원본 command/result는 Work 사실 데이터에 보존한다.
- 전환용 importer는 Work application의 제한된 source 조회와 link API만 사용한다. 이관 후 상태 변경 효과와 대응 Lineage는 같은 Mutation ID로 연결하고, 재실행 시 기존 연결을 반환한다.
- 기록 전용 효과와 작업일만 바뀐 보정은 난 묶음 상태 변경이 없으므로 Mutation 연결을 만들지 않는다.
- 작업 무효화 API는 먼저 영향 범위와 차단 사유를 조회하고 실행 시 같은 조건을 잠금 아래 다시
  검증한다. 동일 무효화 요청은 기존 결과를 반환하고 다른 요청으로 중복 무효화할 수 없다.

## 7. 작업 모듈 내부 구조

`application`, `domain`, `dto` 코드는 `operation`, `target`, `effect`, `correction` 기능 패키지로 구분한다. 계층마다 같은 기능 경계를 사용해 작업 본체, 대상, 적용 효과, 보정 계약의 위치를 일관되게 유지한다.

- `WorkOperationPlanService`: 대상 미리보기, 계획·일괄 계획·즉시 완료 기록 생성
- `WorkOperationProgressService`: 전체·대상 상태 전이와 자동 완료
- `WorkOperationQueryService`: 상세·목록·난 묶음 이력 조회와 응답 조립
- `StructureChangeExecutionService`: 자리 이동·분갈이·분주·합식 회차 실행과 멱등성·잔여 수량 검증
- `DiscardRecordService`: 일반 폐기 기록과 자리 이동 후 원래 자리에 남은 난의 연관 폐기 작업 생성·완료
- `InboundPottingPlanService`: 포트 후보 조회와 품종별 계획 생성
- `ImmediateWorkExecutionService`: 대상 단건·대상 없는 시스템 작업 즉시 실행
- `WorkEffectProcessor`: handler 선택과 실행
- `WorkEffectStore`: 효과·원본/결과 난 묶음 연결 저장과 효과 키 멱등성 확인

자리 이동·분갈이·분주·합식의 공통 N:M 변환은 `StructureChangeExecutor`가 같은 품종 원본을 실행 회차 단위로 합쳐 처리하고 `MovementStrategy`, `RepotStrategy`, `DivideStrategy`, `MergeStrategy`가 작업별 수량 규칙과 계보 유형을 제공한다. 자리 이동의 명시적인 1:1 전량 위치 변경은 이 실행기에서 기존 난 묶음을 일괄 이동하는 분기로 처리한다. 포트 작업은 입고 기록이 원본이므로 `InboundPottingExecutor`의 별도 흐름을 유지한다.

작업 완료일 기본값은 `Asia/Seoul` 업무일자를 사용한다. 상태 변경 시각, 효과 적용 시각과 대상
스냅샷 시각은 UTC로 저장하고 API 응답에서만 `Asia/Seoul`로 변환한다. 테스트에서는 고정
`Clock`으로 저장·응답 시간 규칙을 검증한다.

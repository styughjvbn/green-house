# 전표 이미지 처리: 동작·검증·성능

Green House에서 코어를 사용·수정할 때 필요한 기술 기준입니다. 2026-10-16 이식 기록과 2026-10-17 보완 검증과 2026-10-18 양식별 행 판정 변경을 구분해 기록합니다. Windows 성능 수치는 이식 당시 결과이며 최신 Ubuntu 검증과 같은 측정으로 간주하지 않습니다.

## 1. 처리 흐름

코어는 Java 21과 OpenCV 4.9.0-0으로 동작합니다. Spring·HTTP·DB에 의존하지 않으며 OCR이나 GPU를 사용하지 않습니다. 입력은 사진의 `byte[]`, 출력은 `ProcessingResult(report, images)`입니다. `images`는 파일명 → 이미지 바이트의 Map이며 `report`는 Java record입니다. 디스크 저장은 호스트가 담당합니다.

| 단계 | 처리 | 결과·실패 시 동작 |
|---|---|---|
| 입력 정규화 | 이미지 디코딩, EXIF 방향 반영, 긴 변을 maxDimension 이하로 축소 | 작은 입력은 확대하지 않음. 빈 입력·20MiB 초과·디코딩 실패·60MP 초과 거부 |
| 방향 보정 | 표선 방향·주요 표의 국소 인쇄 밀도로 0/90/180/270도 추정 또는 수동 회전 | 수동 지정도 비스듬한 기울기 보정은 계속 수행 |
| 원근·기울기 보정 | 외곽 컨투어의 네 점 검출, 원근 변환 | 네 변 모두에서 종이 안팎의 색상 차이를 확인. 불확실하면 표선 보정 또는 사진 유지 |
| 표·격자 검출 | 적응형 이진화와 가로·세로 morphology opening, 선 투영으로 경계 추출 | 가로 경계 3개 이상·세로 경계 5개 이상인 후보만 채택. 안정적인 표가 없으면 빈 행을 제거하지 않음 |
| 종이 분리 | Lab 색상·GrabCut·외부 컨투어로 배경을 구분하고, 표 간격과 헤더 보존 높이로 문서 분리 | 표 너비 비율·왼쪽 정렬 차이로 분리 후보를 배제하지 않으며, 분리 전에는 양식·잉크 비율을 판정하지 않음 |
| 문서별 행 판정 | 분리 문서 내부의 표에서 수탁증형/상장의뢰서형 구분 → 격자와 선택지 영역 제외 → 행별 잉크 비율 분석 | 미확인 양식은 행 보존. 표 전체가 문서에 속하는지 확인할 수 없으면 분석 생략 |
| 축약 | 분석한 행 제거 구간으로 표와 문서 축약 | 연속 빈 행의 첫 행은 유지하고 두 번째 행부터 문서 하단 절단. 그 밖의 빈 행·원본 분리 문서는 유지 |

종료 표시 검출은 사용하지 않습니다. 같은 표 안에서 실제 행 경계가 맞닿은 빈 행이 2개 이상 연속되면, 그 연속 구간의 **두 번째 빈 행 시작 높이**부터 분리 문서의 하단 전체를 자릅니다. 아래에 필기·합계·안내문·다른 표가 있어도 함께 제외합니다. 단독 빈 행은 그대로 유지하며 행을 이어 붙이거나 위쪽 내용을 이동시키지 않습니다. 헤더·미확인 행·좌표가 끊긴 행은 연속 빈 행으로 세지 않고, 서로 다른 표의 빈 행도 합산하지 않습니다. 문서별로 가장 먼저 나타난 구간을 사용하며 다른 문서에는 적용하지 않습니다. 보고서의 제거 사유는 `CONSECUTIVE_EMPTY_ROWS_CUTOFF`입니다. 연속 2개가 없으면 표 밖 내용까지 포함한 분리 문서를 그대로 유지합니다.

기본 빈 행 기준은 잉크 비율 **1.5% 이하**이며, 연속 **2개 이상**이면 첫 빈 행은 남기고 두 번째 빈 행부터 자릅니다.

빈 행 판정은 두 양식의 고정된 표 구조를 기준으로 합니다. 헤더에서 여러 칸이 합쳐졌다가 아래 행부터 나뉘는 구조를 우선 확인하고, 세로 경계의 상대 너비 비율로 지원 양식을 보조 확인합니다. 수탁증형은 헤더에서 없던 여러 세로 분할이 아래 두 행에서 연속으로 확인되는 위치를 본문 시작으로 사용합니다. 선이 흐리다는 이유만으로 병합으로 판단하지 않도록 헤더의 다른 세로 구분선도 확인합니다. 고정된 1px 대신 열 간격에 제한된 주변 띠에서 행별 선 존재 여부를 계산해 작은 기울기를 허용하며, 기울어진 가로선이 가까운 투영 경계 두 개로 검출한 좁은 구간은 구조 판정에서 제외합니다. 상장의뢰서형은 병합 구조가 없고 처음 두 유효 행의 내부 열 구분선이 이어지는지 확인하며, 선을 확인할 수 없으면 미확인으로 유지합니다. 수탁증형의 `특상·특·상·보` 네 칸 전체는 내용 판정에서 제외합니다. 그 영역의 동그라미·필기만 있는 행도 빈 행으로 처리될 수 있다는 정책이며, 남기는 행의 실제 이미지에서는 선택지·필기를 지우지 않습니다. 꽃대·꽃송이와 품종명·수량 등 나머지 칸은 계속 계산합니다. 상장의뢰서형은 선택지 제외 없이 계산합니다.

격자 제거 후 각 행 내부의 잉크 픽셀 수를 계산 대상 면적으로 나눕니다. 수탁증 선택지 영역은 분자·분모에서 함께 제외합니다. 행 높이 정규화, 행 간 70% 반복 픽셀 추정, 연결 성분 면적에 의한 행 잉크 필터링, 파란 잉크 재포함은 사용하지 않습니다. 같은 위치에 반복된 검정 필기도 그대로 계산합니다. 빈 행 판정과 문서 하단 절단에는 색상별 보존 분기가 없습니다. 기존 회전 방향 추정에서 사용하는 색상 분석은 유지합니다. 검출한 헤더 행 수와 `protectedTopRows` 중 큰 수만큼 보존하며, 나머지 행은 `minimumInkRatio` 이하일 때 빈 행으로 분류하고, 문서별 연속 2개 조건을 충족할 때만 하단을 제거합니다. 양식이 미확인이면 빈 행 판정을 생략하고 안내합니다. 기존 회전·문서 분리는 별도 단계로 유지합니다. 작은 얼룩이나 휘어진 격자 잔여물도 잉크 비율에 포함될 수 있으므로 임계값이 오삭제·미제거에 영향을 줍니다.

상하 방향은 고정 밝기가 아니라 주변 밝기를 기준으로 이진화한 획을 비교하며, 작은 하단 표가 주요 표보다 방향 판단에 큰 영향을 주지 않도록 합니다. 표 밖 상단에 큰 인쇄 제목이 확인되면 하단 메모 때문에 180도로 뒤집지 않습니다. 네 변 중 일부만 어두운 큰 표 테두리는 문서 외곽으로 확정하지 않아 상단 거래처·날짜의 잘림을 방지합니다. OCR 없는 방향 판정은 여전히 검토 대상입니다.

보정 추정에는 긴 변 최대 1024px의 분석 이미지를 사용하며 작은 입력은 확대하지 않습니다. 공간 임계값은 분석 배율에 맞춥니다. Hough 선 탐색을 한 번 수행해 자동 방향·기울기·표선 원근 추정에서 공유하며, 변환 후에는 검출 선의 끝점 좌표를 행렬로 옮깁니다. 선이 3개 미만이면 처리 해상도에서 선을 다시 검출합니다. 최종 표가 없거나 양식·문서 소속을 확인하지 못하면 첫 시도의 버퍼를 해제하고 처리 해상도로 전체 분석을 한 번 재시도하며 안내를 반환합니다. 처리 해상도에서는 방향 판정과 보정 후 선을 다시 검출합니다. 분석 이미지에서 구성한 회전·원근 변환을 처리 이미지 좌표로 환산하고 합성해 컬러 처리 이미지는 한 번만 보간합니다. 원본 좌표 역변환에도 실제 합성 행렬을 사용합니다. 보정 후 행 판정을 위한 정밀 격자는 처리 해상도에서 별도로 검출합니다. 단순 90도 단위 회전만 필요하면 보간 없이 회전하며, 기존 방향 판정의 검토 필요 정책은 유지합니다.

하나로 연결된 종이 영역 안에서는 위쪽 표 하단과 다음 표 상단의 거리가 두 표의 평균 본문 행 높이 × `documentSeparationRowMultiplier` 이상일 때 문서를 분리합니다. 기본 배수는 5.5입니다. 본문 높이는 잉크 판정 전 격자 좌표로 추정합니다. 가로선이 5개 이상이면 첫 두 구간을 제외하고, 남은 구간 중 중앙값의 0.5–1.5배 범위만 평균에 포함해 좁은 중복 선과 큰 병합 구간의 영향을 줄입니다. 어느 표든 행 높이를 구할 수 없으면 분리하지 않습니다. 처음부터 배경으로 떨어져 있는 종이들은 각각 추출합니다.

절단 위치는 아래 표 상단에서 평균 본문 행 높이 × `documentHeaderRowMultiplier`(기본 7)를 뺀 높이입니다. 위쪽 표를 침범하면 위 표 하단 + 배율 보정된 12px로 제한하고 아래 표 상단은 넘지 않습니다. 가로로 곧게 절단하며 분리 단계의 Canny·Hough 경계선 탐색과 색상 변화 탐색은 사용하지 않습니다. 배경을 구분하는 Lab·GrabCut과 앞단의 원근·기울기 보정은 유지합니다. 실제 종이 윗변을 추적하는 방식이 아니므로 인접 문서의 여백이 포함되거나 7행보다 큰 헤더가 잘릴 수 있습니다. 제목·거래처·날짜와 마지막 품목의 보존을 결과 이미지로 확인해야 합니다. 표를 검출하지 못한 문서는 이 계산으로 복구하지 않습니다.

서버 설정은 `sales.document.image.document-separation-row-multiplier`(기본 5.5)와 `sales.document.image.document-header-row-multiplier`(기본 7)입니다. 코어에서는 각각 `withDocumentSeparationRowMultiplier`, `withDocumentHeaderRowMultiplier`로 변경하며 양의 유한수만 허용합니다.

처리 순서는 **사진 보정 → 표·격자 위치 탐색 → 문서 분리 → 문서별 양식·행 분석 → 축약**입니다. 분리에는 표의 기하 정보만 사용하며 행 판정 결과를 전달하지 않습니다. 분리된 문서의 좌표계에서 분석하고, 보고서의 표·행 좌표는 보정 사진 좌표로 변환해 반환합니다. 투명 배경은 분석에서 제외하며, 표가 문서 경계를 넘거나 투명 부분에 걸리거나 여러 문서에 중복 소속되면 해당 표를 보존하고 문서 축약을 생략합니다. 어느 문서에도 속하지 않은 표도 보존합니다. 문서가 하나도 분리되지 않으면 안내 후 전체 사진을 하나의 분석 범위로 사용하며 분리 문서를 임의 생성하지 않습니다.

사진으로 등록은 자동 입력 전에 문서 영역을 지정하도록 안내합니다. `전체 자동 지정`은 아직 문서 영역이 없는 원본만 설정된 동시 처리 수만큼 처리하며, 기존에 지정한 문서는 유지합니다. `SALES_DOCUMENT_IMAGE_WORKERS` 하나를 백엔드와 Next.js 서버에 동일하게 전달하며 기본값은 3입니다. 1이면 순차 처리합니다. Next.js가 실행 시 읽은 값을 런타임 컨텍스트로 전달하므로 화면에 설정을 노출하지 않고 재빌드도 필요하지 않습니다. 두 프로세스의 환경변수를 바꾼 후 재시작해야 합니다. 여러 사진이 동시에 완료되어도 다운로드 전에 문서 자리를 예약해 전체 10개 제한을 지키며 실패하면 예약을 반환합니다. 완료 개수와 처리 중인 모든 사진을 표시합니다. 사진별 회전 설정과 전체 문서 10개 제한을 적용하고 진행 번호를 표시합니다. 한 사진이 실패해도 나머지는 계속 처리하며 실패한 사진은 개별 재시도할 수 있습니다. 전처리 진단 코멘트는 화면에 표시하지 않고 처리 실패만 안내합니다. AI 자동 입력에서 나온 검토 안내는 유지합니다. `수동 지정`으로 원본에 사각형을 직접 그리거나, `자동 지정`으로 문서 상단과 빈 행 절단 후 표를 포함한 `paper-XX-compacted.png`를 가져옵니다. 문서 영역이 만들어지면 `수동 지정` 버튼이 `영역 수정`으로 바뀝니다. 자동 지정과 수동 적용의 진행 상태를 구분하고 원본 목록에 영역 지정 필요·완료를 표시합니다. 지정한 영역의 이미지는 흰 배경 JPEG 자식 사진으로 보관하고 원본과 나란히 비교합니다. 추출된 문서만 AI 자동 입력·전표 첨부에 사용하며 원본·다른 진단 결과를 대신 전송하지 않습니다. 자동 처리 결과를 다운로드한 뒤 서버의 임시 미리보기는 해제합니다.

크롭 문서를 선택하고 입력 폼으로 내려가 상단 사진이 보이지 않으면 상세 패널 안에 작은 문서 미리보기를 띄웁니다. 클릭하면 기존 확대 뷰어를 열고, 길게 누른 뒤 드래그하면 상세 패널 범위 안에서 위치를 옮깁니다. 방향키 이동도 지원합니다. 상단 사진이 다시 보이면 플로팅을 숨기고 원래 사진으로 확인하며, 문서를 바꾸면 해당 문서의 미리보기와 위치로 초기화합니다.

자동 처리기는 실제 영상에 적용한 축소·회전·원근·기울기 변환의 역변환을 보관합니다. 축약 문서의 범위를 EXIF 방향이 반영된 원본 좌표로 되돌린 외접 사각형을 제공하며, 원본 미리보기에 표시합니다. 사용자는 원본에서 사각형을 이동·크기 조절하거나 수치로 수정할 수 있습니다. 영역 편집은 필요한 Cropper.js 컴포넌트만 편집창 진입 시 불러오며, 조작 중 좌표는 편집기가 관리하고 조작 종료 시 작성 초안에 반영합니다. 여러 영역의 이미지는 원본을 한 번만 디코딩해 순서대로 생성하고 사용한 bitmap·canvas를 해제합니다. 수동 적용은 지정한 원본 사각형을 잘라내며 자동 원근·빈 행 보정을 다시 수행하지 않습니다. 변경된 문서는 새 사진 ID와 빈 입력 초안으로 교체하고 이전 AI 대화의 사진 연결을 해제합니다. 변경하지 않은 문서는 유지하며, 저장 완료·저장 결과 확인 중인 문서는 영역을 잠급니다.

종이 개수와 표 개수는 다릅니다. 한 전표에 두 표가 있어도 관측한 종이 경계가 없으면 두 장으로 나누지 않습니다. 전표 분리와 문서별 행 분석이 끝나면 문서 헤더와 표 밖 내용을 유지한 채 연속 빈 행에 따른 하단 절단 이미지를 추가로 만듭니다. 가려진 내용을 복원하지 않습니다.

## 2. 결과와 조정 값

### 사용할 결과

운영(`PRODUCTION`) 결과는 흰 배경 JPEG(품질 92)이며 아래 파일명의 `.png` 대신 `.jpg`를 사용합니다. `REVIEW`·`ALL`은 마스크와 투명 배경 검토를 위한 PNG를 유지합니다. 문서 분석은 인코딩 전 메모리 이미지와 알파 마스크를 사용하며 중간 PNG 압축·재디코딩을 하지 않습니다. 호스트 미리보기 API는 JPEG를 반환하고 프론트는 재압축 없이 첨부합니다.

| 결과 | 용도 |
|---|---|
| `01-corrected.png` | 회전·원근을 보정한 전체 사진. 빈 행은 잘라내지 않음 |
| `table-XX-compacted.png` | 연속 빈 행 절단 기준을 적용한 표 영상. 문서 절단 높이보다 아래의 표는 생성하지 않음 |
| `paper-XX.png` | 전표별로 분리한 투명 배경 PNG. 빈 행은 잘라내지 않음 |
| `paper-XX-compacted.png` | 분리 문서 상단부터 연속 빈 행 절단 높이 위까지 유지한 PNG. 절단 조건이 없으면 분리 문서 전체 유지 |
| `report` | 보정 방식, 회전, 표·행·종이 좌표, 제거 사유, 경고·검토 필요 여부 |

문서 축약은 표 크롭과 같은 절단 높이를 사용하며, 문서 폭·절단 위의 픽셀·투명도·행 간격을 유지합니다. 마지막 표 끝이라는 이유로 하단을 자르거나 파란 필기만 별도로 보존하지 않습니다. 표가 없거나 표가 문서 경계를 벗어나거나 세로 구간이 겹치면 축약 문서 이미지를 만들지 않습니다. 잘림·겹침은 경고로 안내하며 기존 분리 문서는 유지합니다. 표 안쪽과 주변의 작은 보호 영역은 종이 색상 마스크가 그림자를 배경으로 오인해도 보존하며 관측된 겹침 경계를 넘지 않습니다. 이는 배경 투명화 방지이며 하단 절단 조건을 변경하지 않습니다. 원본 보고서의 좌표는 절단 전 보정 영상 기준을 유지합니다.

표·종이 PNG는 검출된 영역 중 절단 후 남는 대상에만 존재합니다. `report.json`은 데모가 report를 직렬화한 파일이며, 코어가 JSON이나 파일을 직접 저장하지는 않습니다. 표·행·종이 좌표는 최종 보정 영상 기준이고 `documentCorners`만 EXIF 반영 후 원본 영상 좌표입니다. `reviewRequired`는 검토 필요 표시이며 신뢰도 점수나 정확도 확률이 아닙니다.

미리보기 API는 요청별로 잉크 비율을 조절할 수 있으며, 생략하면 기본 비율을 사용합니다. 허용 범위와 요청 형식은 판매 OpenAPI를 기준으로 확인합니다. 화면의 회전 선택과 서버의 이미지 크기·실행 제한은 유지합니다.

### 주요 옵션

| 옵션 | 기본값 | 사용할 때의 기준 |
|---|---:|---|
| maxDimension | 2048 | 800–3000. 낮추면 처리량·메모리를 줄일 수 있지만 작은 필기가 사라질 수 있음 |
| rotationDegrees | -1 | 자동. 오판하는 양식은 시계 방향 0/90/180/270도로 지정 |
| protectedTopRows | 2 | 최소 상단 보존 행 수, 1–10. 확인된 양식의 실제 헤더가 더 길면 헤더 끝까지 보존 |
| documentHeaderRowMultiplier | 7 | 아래 표 위에 남길 헤더 높이의 평균 본문 행 높이 배수. 양의 유한수 |
| documentSeparationRowMultiplier | 5.5 | 연결된 종이의 표 사이 최소 간격을 평균 본문 행 높이의 배수로 지정. 양의 유한수 |
| minimumInkRatio | 0.015 (1.5%) | 빈 행 판정 잉크 비율, 0–0.1. 높이면 필기 있는 행을 삭제할 위험도 증가 |
| outputMode | ALL | 운영 호출은 PRODUCTION을 명시. 검토할 때 REVIEW, 상세 진단은 ALL |

`PRODUCTION`은 전체 보정·검출된 표/종이 JPEG와 report, `REVIEW`는 PNG 결과에 행 판정·종이 윤곽 표시, `ALL`은 선 표시와 수평·수직·종이 마스크까지 생성합니다. 선택하지 않은 진단 영상은 복제·그리기·인코딩부터 생략합니다. 모드 간 보고서 동일성·출력 크기와 운영 JPEG의 흰 배경을 테스트합니다.

기본 처리 크기는 2048px이며, 내부 임계값의 기존 보정 기준 2200px은 유지합니다. 길이 임계값은 `s = min(원본 긴 변, maxDimension) / min(원본 긴 변, 2200)`에, 면적은 `s²`에 비례합니다. 색상·각도·잉크 비율은 유지하며 내부 최대 900px 종이 분석은 별도 좌표계 배율을 적용합니다. 비례 조정은 저해상도에서 같은 판정을 보장하지 않습니다. 최종 보정 캔버스는 회전·원근 변환 때문에 maxDimension보다 커질 수 있습니다.

## 3. 실행·메모리 계약

- `SlipProcessors.bounded(...)`로 생성한 인스턴스 하나를 Spring 싱글톤으로 공유합니다. `process()`도 같은 제한 실행기에 제출하고 기다리며, `processAsync()`는 Future를 반환합니다. 저수준 `new SlipProcessor()`는 제한을 우회합니다.
- 코어 기본은 worker 2개·대기열 4개·OpenCV 내부 스레드 1개이며, Green House 서버는 기본 worker 3개를 사용합니다. 한도는 실행기 인스턴스별이며, 포화되면 `ProcessingRejectedException`으로 즉시 거절합니다. OpenCV 스레드 설정은 JVM 전체에 적용됩니다.
- 비동기 loader는 worker 확보 후 파일을 읽으므로 대기열에 원본 바이트 전체를 보관하지 않을 수 있습니다. 호스트는 요청 종료 후 사라지는 업로드 임시 파일의 수명을 별도로 관리합니다.
- Mat·ROI·커널·컨투어·이미지 인코딩 버퍼의 픽셀 참조는 단계별 scope/finally에서 명시적으로 release합니다. 윤곽 검출이 반환한 목록은 순회 전에 전체를 해제 관리에 등록하며, 검출 중 부분 결과가 남거나 첫 윤곽 처리에서 예외가 발생해도 등록된 버퍼를 scope 종료 시 해제합니다. 호출자는 Mat을 받지 않으며 반환된 이미지 byte[]와 파일 저장 메모리를 관리합니다. Java Mat wrapper의 native header 삭제에는 finalization 동작도 남아 있습니다.
- 취소·interrupt는 실행 중 JNI 연산을 즉시 멈추지 않습니다. 실제 반환까지 worker를 점유합니다. 같은 worker의 loader/callback에서 같은 실행기로 동기 재진입하거나 close하지 않습니다.
- Bean 종료 시 close를 호출합니다. 종료 대기 한도 초과는 예외로 알리며 실행 중 native 작업이 남을 수 있습니다.

`-Xmx`는 native 메모리까지 제한하지 않습니다. 입력은 축소 전에 디코딩하므로 maxDimension만으로 원본 디코딩 메모리를 제한할 수 없습니다. worker/queue 제한도 호스트의 업로드 버퍼·완료 결과·ZIP·파일 저장 메모리를 제한하지 않습니다.

2026-10-16 Windows x64 / Java 21.0.9 / OpenCV 4.9.0-0에서 측정했습니다. 입력은 `20260816_091446.jpg`, 3000×4000 JPEG 약 3.03MiB, 자동 회전·maxDimension=2200·`-Xmx1200m`입니다. 단일 실행은 worker=1·queue=1·OpenCV 스레드=1이며 기동·저장을 포함한 배치입니다. CPU 모델은 기록되지 않았습니다. **Ubuntu 서버의 성능 기준이나 p95 보장값으로 사용할 수 없습니다.**

같은 사진을 `PerformanceProbe`로 PRODUCTION 모드에서 처리했습니다. probe는 PNG를 메모리에서 생성하지만 파일 저장·HTTP·ZIP은 포함하지 않습니다. 매번 결과를 소비하고 전체 결과를 누적하지 않았으며 명시적 System.gc()도 호출하지 않았습니다.

### Ubuntu에서 확인할 항목

Green House의 실제 업로드·저장 경로에서 같은 입력 세트로 worker 1과 2를 비교합니다. 이미지 크기·maxDimension·출력 모드·JDK/OpenCV·CPU/RAM·컨테이너 제한을 함께 기록합니다. 대표 양식의 처리 결과를 확인하면서 요청 지연 p50/p95, 처리량, 프로세스 RSS 또는 컨테이너 메모리, CPU, 거절 수와 장시간 반복 추이를 측정합니다. queue만 늘려 동시 처리량을 높이려 하지 않습니다.

코어·호스트 회귀 검증은 Green House backend에서 실행합니다.

```bash
./gradlew :slip-image-core:test check bootJar --no-daemon
```

기존 배치 측정을 원본 저장소에서 다시 실행하려면 별도로 준비한 사진 폴더를 사용합니다. 아래 시간은 파일 저장과 JVM 기동을 포함하며 코어 probe 수치와 직접 비교하지 않습니다.

```bash
bash mvnw -pl slip-image-demo -am package -DskipTests
/usr/bin/time -v java -Xmx1200m \
  -jar slip-image-demo/target/slip-image-processor-1.0.0.jar \
  --batch /path/to/photos /path/to/results \
  --max-dimension=2200 --workers=1 --queue-capacity=1 \
  --opencv-threads=1 --output-mode=PRODUCTION
```

Green House로 이식한 뒤에는 이 문서도 `docs/image-processing/PROCESSING.md` 등에 함께 보관합니다. 기존 Windows 수치는 기준 기록으로 남기고 Ubuntu 결과를 환경·입력·측정 방법과 함께 추가합니다.

# 판매·경매·정산 관리

## 1. 목적

판매 관리는 일반 판매 전표, 경매장 출하 전표, 경매 lot 추적, 경매 정산, 입금 확인을 함께 다룬다.

기본 흐름:

```text
일반 판매
→ 판매 전표
→ 입금 확인

경매 판매
→ 경매장용 판매 전표 생성
→ 작성중 저장 또는 출하 완료 저장
→ 출하 완료 시 AuctionShipment 생성
→ 전표 항목별 AuctionShipmentLot 생성
→ 경매 결과 / 유찰 / 반환 추적
→ 경매 정산
→ 입금 확인
```

### 판매 관리 v2 화면

기존 `/sales` 판매 관리와 별도로 `/sales-v2`의 `판매 관리 v2`를 제공한다. 두 메뉴는 같은 전표·거래처·수납·경매 데이터와 서버 업무 계약을 공유한다.

- 전표: 일반 판매·경매 출하 통합 목록과 기존 등록·수정·출고/출하·취소·A5 출력. 일반 판매 거래금액을 표시하고 경매 금액은 경매 화면에서 확인한다. 동작 없는 복사, 고정 담당자와 전표의 LOT 표기는 v2에서 제외한다.
- 경매: lot의 결과·후속 결정·실제 반환·도착 취소와 경매 대금 조회. 대금은 같은 경매 페이지에서 열고 출하 목록으로 돌아가며 세 번째 탐색 메뉴를 추가하지 않는다.
- 입금: 대상 미지정 수납 등록·오입력 정정과 전체 수납 조회·다중 배분·배분 정정. 선택 거래처·수납과 업무 화면은 URL로 복원한다.
- 거래처: 기존 기준정보 관리와 선택 거래처의 전표·수납 연결 조회. 선택 거래처는 현재 목록 페이지와 함께 URL로 복원한다.

경매 대금의 결과에서 실제 연결 lot를 조회하고, 수납 배분에서 연결 전표·경매 대금과 입금 이력을 조회한다. 전표의 경매장 출하 링크는 경매장 필터 조회이며 특정 전표의 lot 전체를 확정하는 계약은 아니다. 기존 API에 없는 전표↔lot·lot↔대금의 완전한 역추적과 유형 필터, 실제 자료 기반 매칭 검토 다이얼로그는 후속 범위다. 기존 경매 확인 필요 필터는 유지하며 자동 매칭 상태를 합성하지 않는다.

경매 lot 목록과 대금 목록은 서로 독립된 페이지·크기를 URL에 유지한다. 화면 간 조회 데이터는 Query cache를 공유하고 입력 초안·다이얼로그는 local UI state로 둔다. 은행 수집·예치금·환불 기능은 추가하지 않는다.

### 구조 전환 1단계

구조 전환 1단계에서 Sales 내부의 Document·Direct·Auction·Payment·Partner 경계를 배치했다. 이후 Direct 전용 금액 모델과 유효 배분 조회·검토 차단을 구현했으며 현재 금액 원천은 아래 Direct 구현 절을 따른다. 기존 전표·품목 식별자와 Farm Mutation/receipt/snapshot은 유지한다. 경매 대금 조회·입금 전환과 파생 정산 제거도 반영했다. 실제 경매 매칭·은행 수집은 이번 전환과 분리한다.

| 현재 경로 | 조율과 보존 경계 |
| --- | --- |
| 생성 | Document의 생성 유스케이스가 receipt 접수·전표·allocation·예약·완료 시 출고·잔액·감사를 같은 트랜잭션으로 처리한다. Direct는 일반 판매 회계 port를 구현한다. |
| 수정 | Document가 기존 전표 잠금→이전/신규 거래처 잠금→이전/신규 allocation 일괄 잠금→예약 교체→잔액→감사를 조율한다. |
| 출고·출하 | Document가 난 묶음 잠금→출고 snapshot→Auction port의 shipment/lot 생성→Farm 차감을 조율한다. |
| 취소 | Document가 입금/경매 이력을 확인하고 Farm 복구·예약 해제, Auction 출하 참조 해제·삭제, 잔액·감사를 함께 확정한다. |
| 일반 입금 | Direct 진입점이 트랜잭션을 연다. Direct 대상 adapter가 Document API로 거래처→전표→Direct 금액 순서로 잠그고 Payment가 멱등 확인·금액 반영·원장·잔액·감사를 조율한다. |
| 경매 입금 | Auction 진입점이 트랜잭션을 연다. 경매 대금 대상 port가 거래처→대금 순서로 잠그고 Payment가 같은 입금 처리 순서를 적용한다. |
| 경매 결과·반환 확인 | Auction이 lot 잠금·결과/반환·수량 이력·receipt를 함께 확정한다. 기존 `confirm-return`은 Farm 재고를 생성하지 않는 호환 경로다. |
| 실제 도착·도착 취소 | Auction이 lot 잠금·도착 기록·Farm 생성/보상·수량·감사·receipt를 같은 transaction에서 확정한다. 기존 입고 기능을 호출하지 않는다. |

반환의 목표 정책은 ADR-003을 따른다. 유찰 잔량 전체에 재경매·농장 반환·경매장 처리 중 하나를 선택하고 여러 방법으로 나누지 않는다. 부분 낙찰·부분 도착은 지원 범위이며 농장 반환 결정과 실제 도착을 구분한다. 실제 반환품 생성·배치는 판매 유스케이스에서 Farm API를 사용하고 기존 입고 메뉴·InboundRecord와 연결하지 않는다. 경매장 처리는 결정 시 완료하고 Farm 재고를 변경하지 않는다. 금액 환불과 실물 반환은 별개이며 반환 추정은 과거 이관의 보조 상태다. 구조 전환 이후의 새 후속 결정·실제 도착 API는 아래 구현 절을 따른다. 기존 `confirm-return` 호환 경로는 별도로 유지한다.

도착 후 결정 변경 정책: 유효한 실제 도착 기록이 있으면 변경을 차단한다. 도착 기록 취소 정정으로 Auction 물량과 Farm 재고 효과를 먼저 함께 상쇄한 뒤 다시 결정하며, 취소한 기록은 보존한다. 새 반환 흐름은 이 정책을 실행하며 원래 도착 이력을 보존한다.

## 2. 거래처

거래처 유형:

- `WHOLESALE`
- `RETAIL`
- `AUCTION_HOUSE`

경매장도 거래처로 관리한다. 다만 일반 거래처와 달리 경매 출하 lot, 정산 묶음, 입금 지연일, 정산 단위 설정이 필요하다.

거래처 생성·수정은 감사 이벤트로 보존한다. 감사 스냅샷에는 이름·유형·활성 상태만 저장하고 대표자명, 전화번호, 주소, 메모는 값 대신 변경 필드명만 기록한다.

거래처 관리 목록과 판매 화면의 거래처 선택은 서버에서 검색·페이지 조회한다. 전표 등록은 활성 거래처 중 판매 유형에 맞는 대상을 사용자가 직접 선택하며, 유형을 바꾸면 기존 선택을 비운다. 목록 필터는 비활성 거래처의 과거 전표도 찾을 수 있다. 검색·페이지를 바꿔도 선택한 거래처의 이름과 ID는 유지한다. 비활성 거래처의 이름 조회가 신규 전표 사용을 허용하는 것은 아니며 저장 시 기존 도메인 검증을 유지한다.

## 3. 일반 판매 전표

```text
BusinessPartner
  └─ SalesSlip
      └─ SalesSlipItem
```

규칙:

- 판매 품목은 `SalesSlipItemAllocation`으로 하나 이상의 난 묶음에 배분한다.
- allocation을 만들 때 예약 반영 전 난 묶음 정보를 `CREATION` 스냅샷으로 같이 저장한다.
- 전표 금액은 품목별 수량과 단가의 합계만 관리한다. 공급가액·부가세 정책과 서버 필드가 도입되기 전에는 화면에서 세액을 임의 역산하지 않는다.
- 품목 금액과 전표 합계는 각각 0~2,147,483,647원 범위에서 정확히 계산한다. 생성·수정 시 이 범위를 넘으면 전체 변경을 거절하고, 수정 중 해제한 예약과 관련 이력도 함께 rollback한다. 경매 출하용 0원 단가는 유지한다.
- 배분 합계는 품목 수량과 같아야 한다.
- 배분 대상 난 묶음은 판매 품목과 같은 품종이어야 한다.
- 전표 저장 시 난 묶음 `reserved_quantity`를 증가시킨다.
- 판매 선택 조회와 신규 예약은 Farm의 판매 가능 상태 정책을 공유한다. 주의·이상·병해충 및 비활성 묶음은 선택 목록에서 제외하고, ID를 직접 지정해도 예약을 거절한다. 상태 필터로 이 제한을 우회할 수 없다.
- 수정의 재예약도 현재 상태로 검증한다. 예약된 묶음이 판매 불가로 바뀌면 해당 묶음을 그대로 재예약하는 수정은 거절하고 전체 변경을 rollback한다. 다른 판매 가능 묶음으로 배분을 옮기는 수정은 허용한다. 이미 확정된 예약의 해제·출고·출고 취소 복구는 현재 예약 수지로 처리하며, 판매 불가 전환이 기존 예약을 자동 해제하지 않는다.
- `작성중` 일반 판매 전표는 입금액과 입금 이력이 없을 때 수정할 수 있다. 버튼 가능 여부와 수정 API가 같은 기준을 사용한다.
- 수정 시 기존 예약 수량을 해제한 뒤 새 allocation 기준으로 다시 예약한다.
- 기존·신규 allocation의 묶음 합집합을 ID 순으로 먼저 잠근다. 서로 다른 거래처가 두 묶음의 배분을 맞바꿔도 기존 예약만 먼저 잠그고 상대 묶음을 기다리는 순환을 만들지 않는다. 잠금은 수정 트랜잭션 끝까지 유지하며, 새 allocation 스냅샷은 기존 예약 해제 후의 최신 값으로 저장한다. 실패하면 전표·예약·Mutation·이동·스냅샷·잔액·감사를 함께 rollback한다.
- 수정 예약 해제와 재예약은 각각 `SALES_RELEASE`, `SALES_RESERVE` 이력으로 남긴다.
- 각 수정 실행은 ORM 버전과 별개의 식별자로 예약 해제와 재예약을 연결한다. 품목 규격·메모만 바꾸거나 총액을 유지한 채 배분을 바꿔도 새 예약을 실제로 반영하며, 이미 적용된 Mutation을 재사용할 때는 재고 이동 이력을 중복 생성하지 않는다. 수정 API 재호출은 새로운 편집이며 클라이언트 요청 키 기반 replay를 제공하는 것은 아니다.
- 예약·해제·출고·복구는 Farm Mutation Engine의 typed command를 통과하며 별도 Legacy writer를 두지 않는다. 각 `SalesInventoryMovement`는 같은 transaction의 Mutation ID와 correlation ID를 보존하며, 출고 취소 Mutation은 엔진 전환 후 출고 Mutation을 `COMPENSATES`로 연결한다. 전환 전 출고 이력은 legacy source로 복구한다.
- 수정으로 거래처가 바뀌면 이전 거래처와 신규 거래처의 미수 잔액을 모두 다시 계산한다.
- 같은 거래처의 전표 생성·수정·취소·입금은 거래처 행을 먼저 잠근 뒤 미수 잔액을 다시 계산한다. 잔액 요약에는 낙관적 버전도 저장해 동시 갱신 유실을 막는다.
- 거래처 정산 설정의 최초 조회·변경은 거래처를 잠근 뒤 설정을 조회한다. 동시에 최초 조회해도 기본 설정은 한 건만 생성되고 같은 설정을 반환한다.
- 정산 설정의 저장값과 실행 지원 범위는 구별한다. 현재 직접 판매는 전표별 수동 입금, 경매장은 자료 확인이 끝난 대금의 수동 입금으로 운영하며 설정 응답의 capability가 현재 거래처 유형의 지원 범위를 제공한다. 월간 단위·자동 처리·선입금·규칙 JSON의 기존 선호값은 보존하지만 저장만으로 업무를 실행하지 않는다. 화면은 실행 지원 여부를 서버 capability로 판단하고 저장된 선호값을 실행 중인 기능으로 표시하지 않는다.
- 지연일과 달력일/영업일 방식은 실제 예상 입금일 계산에 사용한다. 자동 매칭·자동 정산·예치금·자동 차감·JSON 규칙 실행은 현재 지원하지 않는다. capability는 지원 기능을 설명하며 권한·특정 전표/정산의 상태별 action을 대체하지 않는다. 새 묶음 정산은 grouping·입금 분배·원본 전표 수정 제한·잔액 중복 방지·취소 이력 계약을 먼저 정한 별도 범위다.
- 현재 수정은 기존 품목 행 재사용 방식이며, 품목 개수 변경은 지원하지 않는다.
- 출고 완료 전표로 상태 변경될 때 실제 `quantity` 차감과 `reserved_quantity` 해제가 같이 일어난다.
- 출고·출하 완료는 allocation의 난 묶음을 ID 순서로 잠그고 `OUTBOUND` 스냅샷을 저장한 뒤 경매 shipment/lot 생성과 재고 차감을 수행한다.
- 전표 취소 시에는 삭제하지 않고 `취소` 상태로 전환한다.
- `작성중` 취소는 예약 수량만 해제한다.
- `출고 완료` 취소는 차감된 실제 수량을 복구한다.
- 출고·출하 취소는 복구할 묶음과 논리 구역을 잠근 뒤 최종 배치 범위·표시 순서를 검사한다. 다른 묶음이 빈자리를 이미 사용했으면 전표 취소·수량 복구 전체를 거부하며, 임의로 위치를 바꾸거나 겹쳐 배치하지 않는다.
- 입금 이력이 있는 일반 판매 전표는 취소할 수 없다.
- 전표 상세 화면의 수정·완료·취소·입금 버튼은 응답의 `availableActions`를 기준으로 표시한다. 서버는 입금 이력과 경매 결과·대금 연결까지 확인해 이 값을 계산하며, 변경 API에서도 같은 규칙을 다시 검증한다.
- 입금 확인은 전표 단위로 기록한다.
- 일반 판매 상태는 `작성중`, `출고 완료`, `취소`만 허용하며 생성 시 `취소` 상태는 허용하지 않는다.
- 판매 목록 화면은 페이지 API를 기준으로 조회한다. 호환용 전체 목록 API는 최신 500건까지만 반환한다.
- 스냅샷은 품종·수량·예약 수량·상태·위치를 과거 시점 분석용으로 보존한다. 기존 자료의 migration 스냅샷은 시점 값을 정확히 복원할 수 없으므로 `MIGRATED_CURRENT_STATE`로 표시한다.

### 후속 결정·실제 도착

유찰 잔량 전체에 하나의 처리 방법을 선택하고 결정 당시 수량·사유·담당자·시각을 별도 이력으로 보존한다. 농장 반환 결정은 재고를 생성하지 않는다. 실제 도착의 수량·상태·논리 구역·배치는 판매 유스케이스에서 Farm Engine으로 별도 묶음을 생성하며, 결정·도착·새 묶음·생성 Mutation을 연결한다. 부분 도착 후 잔량은 같은 반환 결정의 도착 대기로 남는다. 기존 입고 메뉴·InboundRecord·포트 작업을 생성하지 않는다. 경매장 처리는 결정 시 잔량 전체의 처리를 완료하고 Farm 수량을 바꾸지 않는다.

lot 선잠금 뒤 멱등 접수를 확인하고, 도착·Farm 생성·수량 요약·감사·최초 응답을 같은 transaction에서 확정한다. 배치 실패는 전부 rollback하며 같은 요청을 다시 접수할 수 있다. 완료 접수 재전송은 현재 상태를 다시 실행하지 않고 최초 응답을 반환한다. 유효한 실제 도착이 하나라도 있으면 결정 변경을 차단한다. 도착 취소는 Farm 생성 보상과 Auction 수량 복구를 함께 수행하고 원래 기록·새 묶음·보상 Mutation을 보존한다. 후속 사용으로 Farm 보상이 불가능하면 도착 취소와 결정 변경도 완료하지 않는다.

과거 lot 수량·반환 추정·receipt 응답으로 실제 도착 이력이나 Farm 효과를 합성하지 않는다. 날짜 없는 알려진 반환 추정은 새 후속 결정 시 보조 추정량으로 분리하며 실제 도착량으로 취급하지 않는다. 기존 `confirm-return` 호환 동작은 유지하지만 새 후속 결정을 사용한 lot에는 실제 도착·배치 API를 요구한다. 경매 lot 상세에서 후속 결정·실제 도착·도착 취소를 연결한다. 처리 가능 여부는 서버 capability를 따르며 새 화면은 기존 `confirm-return`을 호출하지 않는다. 실제 도착 시 확인한 품종·상태·논리 구역·배치를 입력한다. 도착 이력은 서버 페이지로 조회하고 취소 기록도 보존한다. lot 선택·도착 이력 페이지는 URL에 유지한다. 응답을 받지 못한 요청은 키와 원래 입력을 함께 보존해 새로고침 후 재확인하며, 최초 응답 대신 현재 조회를 다시 읽는다. 반환 추정은 과거 이력을 표시하는 보조 상태이며 새 운영 결과 입력에서 선택하지 않는다. 네 메뉴 개편은 별도 단계다. 금액 환불·parser/matcher·수량 부족/유실 정책은 이번 흐름에서 구현하지 않는다.

### Direct 금액 저장 모델 전환

V43은 일반 판매(과거 유형 미지정 전표 포함)의 저장된 거래금액·지급 예정일·지급 방식과 품목 가격을 Direct 전용 테이블로 그대로 복사한다. 전표·품목 ID를 연결 키로 유지하며 allocation·예약·출고·입금 이벤트를 복제하지 않는다. 신규 전표 생성과 작성중 수정은 기존 전표와 Direct 거래/가격 모델을 같은 transaction에서 저장한다. Direct 저장이나 이후 예약·응답 저장이 실패하면 전표·Direct·Farm 효과·receipt를 함께 rollback한다. 경매 전표에 Direct 거래를 생성하지 않는다. 일반 판매 입금은 Direct 거래금액과 Payment의 유효 배분으로 검증한다. 입금 후 전표의 금액 요약은 이 값으로 갱신하는 조회 projection이며 독립적인 수납 원천이 아니다. Direct 모델은 수납액을 별도로 저장하지 않는다. 상세·목록·출력의 금액은 Direct 거래/가격과 유효 배분으로 조립한다. 생성·수정 금액은 Direct가 계산하고 검색/분석 projection도 이 소유 금액과 유효 배분으로 유지한다.

이전 시점의 전표 수납 요약과 품목 합계, 확인 가능한 수동 입금 연결의 합계를 대사하여 `direct_sale_amount_reconciliations`에 남긴다. 이 표는 이전 시점의 검토 근거이며 현재 수납액 원천이 아니다. 총액·품목 계산·수납·잔액 불일치, 중복/불완전 연결, 해석되지 않은 원장 유형, 과거 음수 표현은 검토 대상으로 보존한다. 같은 입금의 중복 연결은 합계에 중복 반영하지 않는다. 미확인 배분은 임의로 확정하지 않고, 과거 금액 재계산이나 수납 요약을 이용한 새 입금 기록 생성은 하지 않는다. V49는 준비 이후 변경된 projection을 다시 대사하고 전환 시점 불일치 원문을 보존한다. V48은 기존 입금 표시 문구도 Direct 조건으로 원문 그대로 복사한다. 이 문구는 수납 사실이나 입금 가능 여부를 만들지 않으며, 실제 배분 전에는 기존 자유 문구를 유지한다.

Direct의 내부 금액 조회 계약은 전용 거래/가격 모델과 Payment의 유효 수동 배분 합계를 조합한다. 유효 배분은 해당 대상의 거래처와 실제 입금·연결의 거래처가 일치하는 경우만 합산한다. 거래처가 다른 연결은 원장을 보존하되 유효 수납에서 제외한다. 동일 실제 입금의 중복 연결은 한 번만 합산하고, 불완전·중복·미해석 연결과 이전 대사 불일치는 검토 필요로 반환한다. 수동 입금은 이 금액 계약을 사용한다. 전표·거래처를 먼저 잠근 뒤 Direct 금액을 잠그고 현재 배분과 검토 여부를 확인한다. 초과 입금·검토 대상은 실제 원장 생성 전에 거부하며 실패 시 전체 transaction을 rollback한다. 전표 상세·목록·출력은 이 계약을 사용하며 조회만으로 전표 요약이나 원장을 변경하지 않는다. 금액 자료가 없으면 기존 전표 요약으로 대체하지 않는다. 과거 대사에서 검토가 필요한 전표는 새 입금·작성중 수정·Direct 금액 저장을 차단하고 상세의 검토 필요 상태와 업무 capability로 표시한다. 성공했던 입금 키의 재전송은 기존 계약대로 허용한다. 원래 대사 근거를 임의로 수정하거나 일상적인 수정으로 검토를 자동 해소하지 않는다. 검토 해소·정정 유스케이스는 별도 전환 단위다. 조회는 과거 저장 금액이나 원장을 수정하지 않으며, 대상 ID를 나누어 일괄 조회한다.

### 반품 표현 전환 계획 — 미구현

사용자 결정: 거래 타입으로 판매·반품 의미를 표현하고, 수량은 음수를 허용하되 금액은 비음수 값으로 저장한다. 0원 경매 출하의 기존 의미는 보존한다. `DIRECT/AUCTION` 판매 경로 구분과 거래 의미는 별도로 둔다.

구현 시 품목 금액을 절댓값으로 계산할 범위, 거래 타입·수량 부호의 일관성, 매출/잔액 집계의 부호 적용, 실제 반품 입고 시점의 재고 Mutation, 원판매 연결·취소·입금/환불 의미를 함께 정한다. `abs(Integer.MIN_VALUE)`와 곱·합계 overflow를 포함해 정확 연산을 검증한다. 음수 수량만 보고 현재 출고 로직을 역실행하지 않는다.

이번에는 이 모델을 API·도메인에 구현하거나 과거 자료에 backfill하지 않는다. 기존 반품은 음수 수량×양수 단가=음수 금액으로 보존한다. V35의 DB CHECK만 이 과거 표현을 허용하도록 조정하고, 현재 일반 판매 API의 양수 수량·비음수 단가와 정확 연산 검사는 유지한다. 금액 부호만 바꾸면 기존 입금·잔액·매출 사실도 달라지므로 이력 보존 전환과 재대사가 필요하다.

## 4. 경매 판매 전표와 출하 생성

일반·경매 전표의 생성 재전송에는 동일한 `Idempotency-Key`와 입력을 유지한다. 같은 키·같은 입력은 최초 생성 응답을 반환하고, 다른 입력은 `409 / SALES_CREATE_REQUEST_KEY_CONFLICT`로 거절한다. 실제 동일 내용의 새 판매에는 새 키를 사용한다. 키를 생략하는 과거 호출은 매번 별도 신규 전표를 생성하므로 재전송 중복 방어 대상이 아니다.

생성 접수·전표·예약·완료 시 출고/출하·Mutation·재고 이동·snapshot·잔액·감사는 같은 트랜잭션에서 확정하거나 rollback한다. 동시 재전송은 접수 키의 선행 transaction을 기다리며, 실패한 생성은 키를 소비하지 않는다. 재전송은 현재 재고·거래처 활성 여부·전표 상태를 다시 검사하거나 업무를 재실행하지 않는다. 최초 응답의 가능 action과 재고 값은 당시 snapshot이므로 이후 업무 판단에는 현재 상세를 조회한다.

일반·경매 전표 최초 생성은 예약과 필요한 출고/출하를 처리한 최종 상태를 `CREATED` 감사로 남긴다. 인증 계정·세션·요청 식별자는 최초 요청 맥락을 사용하며, 같은 생성 요청의 재전송은 새 감사를 만들거나 실행자를 덮어쓰지 않는다. 키 없는 별도 생성은 각각 감사한다. 감사 저장 실패도 전표·수량·경매 출하·잔액·접수를 함께 rollback하며, HTTP 맥락 없는 내부 호출의 계정과 과거 생성 주체를 추정하지 않는다.

판매 화면은 성공 응답을 받기 전까지 생성 키를 유지하며, 폼을 닫거나 같은 탭에서 새로고침해도 미확인 키를 지우지 않는다. 저장 결과가 불확실할 때 입력을 바꿔 새 전표를 만들기 전에 원래 입력으로 결과를 확인한다. 입력 폼 자체를 브라우저 저장소에 보관하지 않으며, 브라우저 저장소 사용이 제한되면 현재 화면이 유지되는 동안만 키를 보존한다. V38 이전 전표의 요청 identity와 기존 중복 여부는 추정 복원하지 않는다.

현재 기준 도메인 흐름:

```text
AUCTION_HOUSE 거래처 선택
→ 경매 판매 전표 작성
→ 전표 저장
→ 예약 수량 반영
→ 출하 완료 시 AuctionShipment 생성
→ SalesSlipItem 항목별 AuctionShipmentLot 생성
```

즉, 일반적인 운영 시나리오에서는 사용자가 먼저 경매 판매 전표를 작성하고, 그 전표를 기준으로 출하 기록과 lot가 만들어진다.

경매 판매도 일반 판매와 동일하게 품목별 난 묶음 allocation을 먼저 저장한다. lot는 그 allocation을 원천으로 생성된 전표 품목을 따라간다.

취소 정책:

- 경매 전표도 `취소` 상태를 지원한다.
- 경매 시도·결과·상태 이력이 없고 판매·반환 수량과 대금 연결이 없는 대기 출하 전표만 취소 가능하다. 상태를 `WAITING`으로 보정해도 과거 처리 이력은 취소로 지울 수 없다.
- 이력이 없는 출하를 취소할 때 생성된 shipment, lot를 제거하고 난 묶음 수량을 복구한다. 취소는 해당 출하의 lot를 ID 순서로 잠근 뒤 실제 기록을 재검증하며, 결과 입력·반환·수량 보정·상태 변경도 같은 lot root를 잠근다. 결과·이력이 먼저 확정되면 취소를 거절하고, 취소가 먼저 완료되면 삭제된 lot의 결과 입력을 거절한다. 취소 가능 버튼과 변경 API는 같은 기록 기준을 사용한다.
- 경매 판매 상태는 `작성중`, `출하 완료`, `취소`만 허용하며 일반 판매의 `출고 완료`를 사용할 수 없다.

필드 매핑:

- `saleDate` → `AuctionShipment.shipmentDate`
- `partnerId` → `AuctionShipment.auctionHouseId`
- `SalesSlipItem.itemName` → `AuctionShipmentLot.varietyName`
- `SalesSlipItem.genus` → `AuctionShipmentLot.itemName`
- `SalesSlipItem.spec` → `AuctionShipmentLot.shipmentGrade`
- `SalesSlipItem.quantity` → `AuctionShipmentLot.shippedQuantity`

`boxes`는 현재 MVP에서 별도 입력 없이 `null`로 둔다.

경매 출하 선택지는 아직 전표로 변환되지 않은 최신 출하 200건까지만 반환한다.

## 5. 경매 추적

경매는 전표 항목이 아니라 lot 단위로 추적한다.

이유:

- 출하와 실제 판매 시점이 다르다.
- 같은 lot이 유찰 후 다시 경매될 수 있다.
- 일부만 판매되고 일부는 대기 또는 반환될 수 있다.

```text
AuctionShipmentLot
  ├─ AuctionAttempt
  ├─ AuctionResultLine
  └─ AuctionLotStatusHistory
```

출하 등급은 lot 기준으로 유지한다. 결과 행의 등급은 경매장 원본 결과에 표기된 값으로, 원본 결과와 lot의 매칭 분석에 사용할 수 있는 별도 정보다. 미입력·공백 및 서버가 자동 생성하는 유찰·반환 추정 행의 등급은 미상으로 저장하며 출하 등급으로 채우지 않는다. 기존 결과와 Receipt snapshot의 등급은 변경하지 않는다.

현재 운영 입력 방식:

- 경매 판매 전표가 `출하 완료`로 전환될 때 `AuctionShipmentLot` 생성
- 출하 후 `POST /api/auction-lots/{id}/results` 로 수동 경매 결과 입력
- 낙찰/부분 낙찰/유찰/반환 추정을 lot 단위로 기록
- 반환 추정 후 실제 반환일은 `confirm-return`으로 확정
- 낙찰 결과의 수량×단가가 현재 금액 저장 범위를 넘으면 잘못된 금액을 저장하지 않고 입력을 거절한다.
- lot의 결과·반환·수량·상태 변경은 lot 행을 잠근 트랜잭션에서 수행한다. 같은 lot의 같은 경매일·차수 결과는 DB에서도 중복을 허용하지 않는다.

결과 입력·반환 확인의 재전송:

- 두 업무는 lot와 업무 종류별 요청 키로 구분한다. 같은 키·같은 입력의 재전송은 최초 처리 응답을 반환하고 수량·결과·상태 이력을 다시 반영하지 않는다. 같은 키의 다른 입력은 충돌로 거절한다. 실제 다음 경매나 추가 반환은 새 키를 사용한다.
- 자동 차수와 반환 수량 생략은 최초 실행에서만 현재 lot 기준으로 해석한다. 전량 낙찰·반환 완료 후에도 같은 입력을 재전송할 수 있다. 최초 응답은 저장 시점의 이력 ID와 상태를 보존한다. 이후 다른 경매·반환·보정이 있으면 현재 상태는 상세 조회로 확인한다.
- lot 잠금, 결과·반환 반영, 최초 응답과 receipt 저장은 하나의 트랜잭션이다. 저장이 실패하면 모두 rollback하고 같은 키로 다시 시도할 수 있다. receipt는 삭제·기한 만료로 제거하지 않는다. 영속 응답·입력 지문 계약을 바꿀 때는 기존 receipt의 호환도 검토한다.
- 판매 화면은 처리 응답을 받기 전까지 같은 lot·업무의 키를 유지한다. 탭 세션 저장소를 사용할 수 있으면 화면 재진입·같은 탭 새로고침에도 유지한다. 성공 응답을 받은 뒤에는 다음 실제 업무에 새 키를 발급하며, 조회 갱신 실패 때문에 확정된 업무 키를 재사용하지 않는다. 브라우저 저장소가 차단된 환경은 현재 화면에서만 키를 보존한다. 새 탭·새 세션의 입력을 과거 요청으로 자동 판정하지 않는다.
- V36 이전 결과·반환에는 요청 identity가 없어 receipt를 추정 생성하지 않는다. 과거 중복 여부와 정산 영향은 별도 대사 대상이다.

## 6. AuctionLot 상태

- `WAITING`
- `IN_PROGRESS`
- `SOLD`
- `PARTIALLY_SOLD`
- `REAUCTION_WAITING`
- `RETURN_INFERRED`
- `PARTIALLY_RETURNED`
- `RETURNED`
- `QUANTITY_MISMATCH`
- `REVIEW_REQUIRED`
- `CANCELLED`

상태 변경은 항상 이력으로 남긴다.

수량 변경은 상태가 같아도 이력에 판매·대기·반환 수량의 전후값, 처리 시점, 작업자와 사유·메모를 보존한다. 같은 상태의 두 번째 부분 반환·부분 낙찰도 각각 남긴다. 같은 상태·같은 수량의 무변경 요청은 이력을 추가하지 않는다. V37 이전 이력에는 수량 전후값이 없으므로 현재 lot 값으로 역산하지 않고 미상으로 유지한다. 경매 결과 입력에는 작업자 필드가 없어 해당 이력의 작업자는 기존처럼 미상이다.

직접 수량 보정은 경매 시도가 없고 반환 확인일도 없는 lot에만 허용한다. 유찰·반환 추정도 실제 경매 결과이며, 상태를 수동 변경해도 보정 제한은 해제되지 않는다. 결과·정산·입금 또는 확인된 반환을 직접 보정으로 덮어쓰지 않는다. 결과/반환 이후 보상·보정 이벤트는 후속 범위다. 목록·상세의 `quantityAdjustmentAllowed`가 화면의 보정 버튼을 제어하고 서버가 lot 잠금 후 같은 정책을 재검증한다. 이미 저장된 값 그대로 요청한 수량 보정은 변경 없이 반환한다.

수량 이력은 lot 변경과 같은 트랜잭션에 저장하며 결과·반환의 Receipt도 함께 확정하거나 rollback한다. 기존 Receipt의 최초 응답 스냅샷은 수정하지 않는다. 과거 Receipt 재조회에서는 신규 수량 이력 필드와 capability가 미상일 수 있으며 최신 상태는 상세 조회로 확인한다.

## 7. 경매 대금

Auction은 경매장이 제공한 자료 참조·낙찰액·받을 금액과 원본 결과 연결을 소유한다. 결과 합계로 지급액을 추정하지 않는다. 같은 경매장·결과 소유권·검토 상태·제공 낙찰액 일치를 확인하며, 자료 연결과 받을 금액이 확인된 대상만 새 입금을 허용한다. 실제 parser/matcher·자료 수집은 별도 단계다.

Payment는 실제 수납과 유효 배분을 소유한다. 대금 모델에 독립적인 입금액을 저장하지 않는다. 거래처→대금 root 순서로 잠근 뒤 재전송 확인·대상 검증·원장·잔액 활동·감사를 하나의 transaction에서 처리한다. 원래 성공한 키의 재전송은 자료 미확인 상태에서도 실제 기록을 재조회하며, 같은 키의 금액·날짜 변경은 거절한다.

조회는 대금 root 페이지를 먼저 읽고 결과 참조·원본 결과 표시·거래처 이름·유효 배분을 일괄 조립한다. 제공 금액과 미확인 잔액은 null을 유지한다. 화면은 서버의 입금 capability를 사용하며 미확인 값을 0원이나 완납으로 표시하지 않는다. 페이지·크기·선택 대금은 URL에 보존하며 이전 정산 ID를 새 대금 ID로 해석하지 않는다.

V47과 V50은 과거 실제 입금 대상 참조를 미확인 대금으로 연결하고 원래 입금 ID·금액·날짜·부모 연결·멱등키·원본 결과 ID를 보존한다. 이미 확인된 대금은 변경하지 않는다. 원래 대상이 없거나 결과 소유권이 충돌하면 추정 연결하지 않고 이전을 중단한다. 실제 입금이 없는 파생 정산 요약은 새 지급 근거로 복사하지 않는다.

파생 정산 테이블·생성·재계산·시작 초기화·기존 정산 조회와 입금 API를 제거한다. 별도 보관이나 일괄 재구성 기능은 없다. 새 수납과 기존 성공 요청 확인은 경매 대금 API를 사용한다. 거래처의 기존 정산 선호 설정은 보존하지만 경매일별 파생 정산 실행 capability는 제공하지 않는다.

## 8. 입금 처리

입금 이벤트는 `PartnerPaymentEvent`로 보존한다.

대상:

- 일반 판매 전표
- 경매 대금
- 대상 미지정 입금

규칙:

- 입금 이벤트는 삭제하지 않는다.
- 수동 입금 요청은 대상별 `idempotencyKey`를 필수로 받는다. 같은 키·금액·입금일 재요청은 기존 결과를 반환하고, 다른 금액 또는 입금일로 키를 재사용하면 `409 / IDEMPOTENCY_KEY_REUSED`로 거부한다. 입력 오류·초과입금의 기존 `400 / VALIDATION_ERROR`와 구분하며, 충돌 요청은 대상·입금/연결 이벤트·잔액·감사를 변경하지 않는다. 기존 입금 결과를 확인하고 실제 추가 입금에만 새 키를 사용한다.
- 잘못 배분된 입금은 배분 정정으로 기존 연결을 취소하고 필요한 새 배분을 함께 확정한다. 원래 입금액·입금일·식별자는 보존한다.
- 거래처 정산 설정 변경, 수동 입금 이벤트 생성, 대상 전표·경매 대금의 입금 상태 변경은 감사 이벤트로 함께 보존한다.
- 감사 스냅샷에는 입금자명과 메모를 중복 저장하지 않는다.

입금 이력 화면은 실제 입금 이벤트만 서버에서 필터링해 페이지로 조회한다. 연결 이벤트도 원장에 보존하며 전체 이벤트 조회에서 확인할 수 있다. 호환용 전체 목록은 이벤트 기준 최신 500건까지 반환한다. 판매 전표·대금 상세에서는 이력의 열림·페이지를 URL에 유지하고 대상을 바꾸면 초기화한다. 입금 처리 후 해당 대상의 이력을 갱신하며, 이력 조회가 실패해도 완료된 입금을 실패로 표시하지 않는다.

### 대상 미지정 수납과 오입력 정정

은행 자료 없이도 거래처를 지정해 수동 수납을 기록한다. 수납 원본을 보존하고 미배분 잔액에만 반영한다. 전표·대금의 수납액이나 거래처 받을 금액·예치금 잔액을 변경하지 않는다. 다중 대상 배분은 아래 배분·정정 흐름을 사용한다. 예치금 전환·사용은 후속 범위다.

미배분 수납의 오입력 취소는 원본을 취소 상태로 남기고 날짜·사유·실행자와 원본 연결을 갖는 정정 기록을 추가한다. 후속 배분·사용 기록이 있으면 먼저 이를 정정해야 하며, 실제 환불을 의미하지 않는다. 금액·입금일을 고치려면 잘못된 기록을 취소하고 새 수납을 기록한다.

수납·정정은 거래처를 먼저 잠근 뒤 원장·미배분 잔액·감사를 같은 트랜잭션에 반영한다. 거래처별 수납 키와 정정 키는 별도 namespace이며 동일 입력 재전송은 중복 반영하지 않는다. 수납의 금액·날짜·입금 수단·입금자·메모와 정정의 원본·날짜·사유가 다르면 키 재사용을 거절한다. 잔액 저장 한도를 넘으면 전체 변경을 거절한다.

기존 입금 화면의 `대상 미지정 수납` 탭에서 거래처·페이지를 URL에 보존한다. 수납·정정 후 잔액과 이력을 다시 조회하며, 응답 유실 시 브라우저 세션에 저장한 원래 입력·키로 재확인한다. 현재 상태는 재조회 결과를 사용한다. 은행 앱 알림의 휴대폰→webhook 수신은 원본 형식·인증·중복 식별 자료가 확보된 뒤 별도 adapter로 구현한다.

### 다중 배분·배분 정정

`배분·정정` 탭에서 거래처의 수납과 배분 내역을 조회한다. 수납 한 건을 여러 일반 전표·경매 대금에 나누거나 여러 수납을 같은 대상에 합쳐 배분할 수 있다. 거래처·수납 선택·목록 페이지는 URL에 보존한다. 수납과 대상의 배분·정정 가능 여부는 서버 계약을 사용하며, 현재 화면의 잔액 계산으로 허용 여부를 추정하지 않는다.

기존 단건 입금의 연결도 정정할 수 있다. 기존 배분은 취소 상태로 보존하고 원본 연결·날짜·사유·실행자를 갖는 연결 해제 기록을 추가한다. 배분 취소만 수행하거나 새 배분을 함께 지정한다. 취소로 복구된 수납 사용 가능액은 같은 요청에서 재배분할 수 있다. 원래 수납을 다시 만들거나 실제 환불로 기록하지 않는다. 대상의 입금액은 유효 배분 합계로 다시 조회하며, 미배분 잔액에는 원래 대상이 있는 수납의 복구액도 포함한다. 과거 입금 이력이 있다는 이유로 제한하던 전표 수정·취소는 배분 정정 후에도 자동으로 허용하지 않는다.

같은 거래처 안에서 한 번에 새 배분 100건·기존 배분 취소 100건까지 처리한다. 거래처 → 전체 전표 ID 순 → Direct 금액 ID 순 → 경매 대금 ID 순 → 수납 원본 ID 순으로 잠근다. 기존 판매 수정·취소·단건 입금도 거래처 선잠금으로 맞춘다. 유효 배분·수납 수지와 대상 소유권을 대사하며, 과거 금액 검토·미확인 경매 대금·수납 불일치·초과 배분은 차단한다. 배분·연결 해제·대상 projection·잔액·감사·완료 접수는 한 트랜잭션에서 함께 확정하거나 rollback한다. 실물 재고를 변경하지 않는다.

배분과 정정은 거래처별 공통 명령 키 범위를 사용한다. 같은 키·동일 입력은 최초 결과의 이벤트 ID를 반환하고 이후 정정 상태는 상세 재조회로 확인한다. 입력이나 업무를 바꿔 키를 재사용하면 거절한다. 브라우저는 수납·오입력 취소·배분·배분 정정의 미확인 요청을 함께 관리해 다른 화면에서도 원래 입력·키로 확인할 수 있다. 은행 수집·자동 매칭·예치금 사용·실제 환불은 지원하지 않는다.

### 경매 근거 대금의 입금 계약 전환

경매 근거 대금은 별도 서버 페이지와 상세 조회를 제공한다. 경매장 제공 경락액·받을 금액과 실제 유효 입금 배분을 구분하며, 받을 금액이 없는 자료에 경락액으로 잔액을 만들어 넣지 않는다. 연결 결과는 기존 결과 ID로 추적한다. 자료 연결 확인·받을 금액 확인·기존 배분 검토 여부를 함께 판단한 서버 capability로 입금 가능 여부를 제공한다.

입금은 거래처 → 대금 대상 순서로 잠근 뒤 기존 Payment 수납/배분 유스케이스를 사용한다. 수납액은 별도 요약 컬럼을 쓰지 않고 유효 배분 합계로 읽는다. 같은 키·금액·입금일은 추가 수납 없이 현재 조회를 반환한다. 거래처 잔액의 기존 의미를 유지하고 입금 활동만 연결한다. 자료 parser/matcher와 수신 adapter는 이번 단계에서 구현하지 않는다.

V47·V50의 실제 입금 참조 전환과 파생 정산 제거는 위 경매 대금 구현 절을 따른다. 기존 성공 요청은 원래 멱등키로 새 대금 API에서 확인한다. 기존 정산 API와 시작 초기화는 제공하지 않는다.

Direct 생성·수정의 가격과 합계 계산은 Direct의 금액 정책을 따른다. Document는 전달된 금액을 검색·분석·호환 표시용 projection으로 저장하며 실제 수납은 유효 배분 합계로만 갱신한다. V49는 과거 projection을 소유 금액으로 갱신하기 전에 전환 시점의 불일치 원문을 보존한다. 기존 V43 대사 근거·실제 입금 원장·생성 receipt·과거 snapshot·Farm 식별자는 변경하지 않는다. 금액 원천이 누락된 전표는 추정 복사하지 않고 이전을 중단한다. 새 불일치도 검토가 끝날 때까지 입금과 금액 변경을 차단한다.

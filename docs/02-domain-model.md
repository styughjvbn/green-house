# 도메인 모델

## 1. 농장 구조

```text
House
 └─ PhysicalBed
    └─ BedZone
       ├─ BedZoneCapacity
       └─ OrchidGroup
```

### House

농장의 동이다.

- 번호와 이름을 가진다.
- 기본 운영 기준은 15개 동이다.
- 하나의 동은 여러 물리 배드를 가진다.

### PhysicalBed

동 내부의 실제 배드다.

- 기본 운영 기준은 동마다 3개다.
- 실제 농장 방향 기준으로 좌→우 표시 순서를 가진다.
- 길이, 폭, 철사 줄 수, 지지대 간격 같은 참고 정보를 가질 수 있다.
- 실제 농장에서는 "다이" 고 칭한다.

### BedZone

물리 배드를 실제 운영 단위로 나눈 논리 구역이다.

- 기본값은 각 배드의 좌/우 구역이다.
- `LEFT`, `RIGHT`, `CUSTOM`, `HANGING` 같은 구역 방향/유형을 가진다.
- 난 묶음 배치와 작업 이력의 기본 위치 단위다.
- 배치 유형·화분 크기·수용 모드별 `BedZoneCapacity` 설정을 가질 수 있다.

### BedZoneCapacity

논리 구역의 배치 유형별 수용량 설정이다.

- 배치 유형, 표준 화분 크기, 수용 모드, 단위 길이, 수용 수량을 가진다.
- 현재 코드에는 별도 `BedZoneSegment` 엔티티가 없다.
- 난 묶음의 실제 구간은 `OrchidGroup.startPosition`, `endPosition` 숫자 범위로 저장한다.

### OrchidGroup

난 묶음은 현재 시스템의 핵심 관리 단위다.

- 신규 생성·수정 난 묶음은 품종 마스터 연결이 필수다. 마이그레이션된 기존 행은 검수를 위해 품종 연결이 없을 수 있다.
- 품종명, 속, 수량, 예약 수량, 화분 크기, 초기 년생, 상태, 메모를 가진다.
- 하나의 논리 구역에 속하고 구역 내부 시작·끝 위치로 배치된다.
- 같은 구역 안에서 표시 순서를 가진다.
- 이동 시 자리 이동 작업 이력이 자동 생성된다.
- 가용 수량은 `수량 - 예약 수량`으로 계산한다.
- 신규 판매 예약은 Farm 상태 정책상 판매 가능한 묶음에만 허용한다. 판매 선택 조회와 판매 가능 수량 집계도 같은 정책을 사용한다. 상태가 판매 불가로 바뀌어도 이미 확정된 예약의 해제·출고·취소 복구는 기존 예약 수지로 처리한다.
- 연속 작업을 일괄 취소하면서 원본을 최종 생성 취소할 수 있다. 이때 과거 위치로 복구하지 않으며, 작업·계보·원장과 감사 기록은 보존한다. 범위 밖의 유효 참조와 예약 수량은 계속 차단한다.
- 수량과 예약 수량 변경은 `0 <= reservedQuantity <= quantity`를 만족해야 하며, 판매 배분 변경은 난 묶음 행을 잠근 뒤 처리한다.
- 화분 크기는 표준 `potSizeCode`를 가지며 원본 표시 문자열과 분리한다.
- 의미가 불명확한 기존 화분 값은 임의 통합하지 않고 `UNMAPPED`로 검수한다.

### OrchidGroupCollection / OrchidGroupCollectionMember

사용자가 목적에 따라 난 묶음을 지속적으로 묶는 관리 그룹과 소속 이력이다.

- 하나의 난 묶음은 여러 사용자 그룹에 동시에 속할 수 있다.
- 위치, 년생, 화분 크기, 상태가 바뀌어도 소속은 자동으로 바뀌지 않는다.
- 구성원 해제는 소속 행을 삭제하지 않고 `removedAt`을 기록한다.
- 그룹은 삭제보다 `ARCHIVED` 보관을 우선하며, 보관 후 소속 변경을 막는다.
- 같은 그룹과 난 묶음의 활성 소속은 하나만 허용한다.

### DerivedOrchidGroup

품종, 현재 년생, 표준 화분 크기가 같은 활성 난 묶음을 조회 시점에 계산한 자동 그룹이다.

- 별도 엔티티나 동기화 데이터를 저장하지 않는다.
- 그룹 키는 `varietyId:ageYear:potSizeCode` 형식이며 현재 조회 조건을 나타낼 뿐 영구 ID가 아니다.
- 수량 0과 종료·폐기·판매 완료·생성 취소 난 묶음, `UNMAPPED` 화분 값은 제외한다. 주의·이상·병해충 묶음은 치료 작업 등의 대상으로 유지한다.
- 난 묶음 속성이 변경되면 다음 조회부터 기존 그룹에서 빠지고 새 조건의 그룹에 포함된다.

### Variety

품종 기준 정보다.

- 속, 품종명, 별칭, 기본 화분 크기, 판매 사용 여부와 선택 색상(`#RRGGBB`, `null` 허용)을 가진다.
- 선택 색상은 농장 현황과 난 묶음 관리의 품종 색상 구분에 공통으로 사용한다. 색상을 지정하지 않으면 각 화면의 기본 색상 규칙을 사용한다.
- 속과 품종명 조합이 품종의 자연키 역할을 하며, 같은 조합은 중복 등록할 수 없다.
- 연결된 난 묶음 수와 총 보유 수량 같은 요약값 조회 기준이 된다.
- 운영 데이터 보존을 위해 삭제보다 비활성화를 우선한다.

### InboundRecord

입고 기록이다.

- 입고일, 입고 유형, 품종, 예상 수량, 임시 위치, 포트 예정일, 메모를 가진다.
- 유리병 모종은 포트 작업 전까지 포트 작업 대기 상태로 관리하고, 임시 보관 위치와 포트 예정일을 선택적으로 가진다.
- 실제 수량·화분·년생·배치 규격·위치는 입고가 아닌 생성된 난 묶음이 소유한다.
- 즉시 배치 입고의 `placement`는 난 묶음 생성 명령이며 입고 Entity에 중복 저장하지 않는다.
- 입고와 생성 난 묶음은 `OrchidGroup.inboundRecord`로 연결하며 대표 난 묶음을 별도로 두지 않는다.
- 난 묶음이 생성된 뒤에는 취소보다 상태 전이를 우선한다.

### Material

약제, 비료, 일반 자재 기준 정보다.

- 분류, 자재명, 제조사, 규격, 보유 수량, 보관 위치, 사용법을 가진다.
- 작업 기록과 운영 메모 입력 시 정규화 기준으로 사용한다.
- 운영 데이터 보존을 위해 삭제보다 비활성화를 우선한다.

## 2. 작업 도메인

```text
WorkType 1 ─ N WorkOperation 1 ─ N WorkOperationTarget 1 ─ 1 WorkTargetExecution
                                      └─ N WorkAppliedEffect
```

### WorkType

작업 유형이다.

기본 예시:

- 농약
- 비료
- 분갈이
- 상태 기록
- 일반 메모
- 잎 정리
- 잡초 정리
- 단화/꽃 정리
- 자리 이동

사용자 정의 작업 유형을 추가, 수정, 비활성화, 정렬할 수 있다.

### WorkOperation

상위 범위와 그룹을 포함하는 신규 작업 전체 단위다.

- 원본 선택 범위와 실제 난 묶음 대상을 분리한다.
- 일반 작업과 자리 이동·분갈이·분주·합식 기간 계획은 실제 난 묶음 대상을 확정하고, 입고 포트 계획은 난 묶음 생성 전 입고 기록을 대상으로 확정한다.
- 즉시 완료 기록형 작업은 농장 전체, 동, 물리 배드, 논리 구역, 난 묶음 범위를 지원한다.
- 분갈이·분주·합식 작업 기록은 선택한 원본을 품종별로 묶어 각 품종의 전체 수량과 모든 결과를 등록 시점에 입력하고, 품종별 작업 생성·결과 생성·계보·완료를 하나의 트랜잭션으로 처리한다.
- 폐기 작업 기록은 선택한 모든 난 묶음의 폐기 수량·사유를 함께 입력하며, 포트 작업 기록은 선택한 모든 입고 기록의 결과를 입력한 뒤 품종별 완료 작업으로 저장한다.
- 저장 시 실제 대상과 당시 위치·속성·수량 스냅샷을 확정한다.
- 상위 범위 작업은 난 묶음별로 복제하지 않는다.
- 대상별 계획 수량·누적 작업 수량·잔여 수량과 실행 상태를 별도로 가진다.
- 전체 작업은 계획·진행·일시중지·완료·종료·취소·무효화 상태를 가진다.
- `STOPPED`는 완료된 기록과 효과를 유지하고 남은 대상만 종료한 상태다. `CANCELED`는 실행 전 계획 또는 기록 전용 작업을 취소한 상태이고, `VOIDED`는 Mutation 보상으로 구조 변경 효과까지 되돌린 취소 상태다.
- 각 대상은 대기·진행·완료·건너뜀·취소·실패 상태와 처리 시각·작업자·결과 상세를 가진다.
- 대상 완료는 작업 효과 handler를 거치며 효과 적용과 완료 상태 변경을 하나의 트랜잭션으로 처리한다.
- 같은 대상의 같은 효과는 한 번만 적용하고 `WorkAppliedEffect`에 handler, 입력·결과, 적용 시각을 보존한다.
- 작업 효과로 생성되거나 연결된 난 묶음에서도 원인 작업을 통합 이력으로 조회한다.
- 자리 이동·분갈이·분주·합식은 하나의 작업 아래 여러 실행 회차를 둘 수 있으며, 한 회차에서 같은 품종의 실제 원본 N개를 총 투입 수량으로 합친 뒤 결과 난 묶음 M개로 나눈다. 결과별 직접 원본 수량 배분은 만들지 않는다.
- 구조 변경 실행은 계획 잔여 수량의 일부만 처리할 수 있고, 대상은 누적 수량에 따라 부분 완료 또는 완료 상태가 된다.
- 결과 난 묶음은 일반 결과, 분주 후보, 별도 보관으로 구분할 수 있으며 분주 후보와 별도 보관도 원본 계보를 유지한다.
- 구조 변경 실행은 원본을 잠근 뒤 투입 수량을 차감하고 결과 생성·실행 회차 계보·작업 효과를 한 트랜잭션에서 기록한다. `WorkAppliedEffect`가 실행 회차 노드이고 `WorkEffectOrchidGroup`의 `SOURCE`·`RESULT`가 원본과 결과를 연결한다.
- 분갈이와 입고 포트 작업 계획은 생성 시 구조를 바꾸지 않고 대상별 실행 완료 시 결과 위치·수량을 검증해 난 묶음을 생성한다.
- 분주와 합식은 결과 난 묶음 개수를 제한하지 않고, 합식은 원본 난 묶음 하나로도 처리할 수 있다. 각각 `SPLIT_TO`, `MERGED_TO` 계보로 작업 의도를 구분한다. 분주와 분갈이는 결과 수량 합계가 원본 투입 수량보다 커질 수 있고, 합식은 결과와 손실 수량 합계가 투입 수량과 같아야 한다.
- 구조 변경의 손실·증식 수량은 사용자가 입력하지 않는다. 서버가 원본 투입 수량과 최종 결과 수량의 차이로 자동 계산해 작업 효과에 저장한다. 결과가 적으면 손실, 많으면 증식으로 기록하며 둘 중 하나는 0이다.
- 결과 난 묶음들이 같은 품종·년생·표준 화분 크기를 가지면 다음 조회부터 하나의 자동 그룹 구성으로 자연스럽게 묶인다.
- 자리 이동 계획은 원본 대상을 확정하되, 목적 논리 구역과 구간은 대상별 실행 시 입력하고 이동 효과 이력을 한 번만 남긴다.
- 전체 분갈이는 원본을 수량 0·`종료` 상태로 보존하고, 부분 분갈이는 차감 후 잔여 수량으로 계속 운영한다.
- 이전 `work_records` 테이블은 마이그레이션 원본과 감사 데이터로만 보존하며 애플리케이션 도메인과 API에서는 사용하지 않는다.

### WorkOperationCorrection

완료된 구조 변경 작업의 정정은 원본에 속한 감사 이벤트로 보존한다.

- 원본 작업의 완료 상태와 실행 당시 결과 스냅샷을 유지한다. 보정은 독립 작업이 아니며 작업 건수에 포함하지 않는다.
- 작업일·결과 난 묶음의 수량·상태 변경 전후 값, 사유, 담당자, 메모와 정정 시각을 원본 상세에 누적한다.
- 수량 정정은 실행별 `투입 + 증식 = 결과 + 손실`을 만족해야 한다. 잘못 기록한 투입량은 감사 이벤트로 정정하며 원본 난 묶음의 과거·현재 수량을 자동 변경하지 않는다. 증식은 분갈이·분주에서만 허용하고, 이동에 함께 등록된 폐기량은 단독 정정하지 않는다.
- 원본 작업을 잠근 후 결과 난 묶음을 ID 순으로 잠그고, 감사 이벤트·작업일·수량 변경을 같은 트랜잭션에서 확정한다.
- 난 묶음 상태가 바뀌면 보정 이벤트를 출처로 Mutation을 기록한다. 날짜만 정정하면 Mutation을 만들지 않는다.
- 후속 작업·이동·판매·입고 연결이 있거나 예약 수량보다 작게 줄이려는 보정은 거부한다.
- 결과 생성 취소는 원래 생성 사실을 보존한다. 새 결과 생성과 계보 교체 보정은 후속 범위다.
- 난 묶음 관리의 생성 취소는 연결 작업이 모두 `CANCELED`·`VOIDED`인 경우에도 허용한다. 취소되지 않은 작업(남은 작업 종료 포함), 판매·입고 연결, 예약 수량이 남아 있으면 차단하고 원본 행과 모든 이력은 보존한다.

### 실사 수량 감사 기록

- 실사 수량 조정과 작업 기록의 수량 정정은 현재 기본 비활성화 상태다. 아래 수량 정책과 감사 모델은 재개를 위한 구현 기반으로 보존한다. 작업일·상태 정정과 결과 생성 취소는 유지한다.

- 현재 업무일에 직접 확인한 수량을 난 묶음에 반영한다. 차이는 실사 차이이며 폐기·증식이나 과거 작업 오류로 자동 분류하지 않는다.
- 독립 작업을 생성하지 않고 Farm 소유 감사 기록과 수량 전후 Mutation을 같은 트랜잭션에 보존한다. 과거 작업 스냅샷·상태·위치·계보는 변경하지 않는다.
- 확인 당시 revision이 변경됐거나 예약 수량을 침해하면 거부한다. 종료·폐기·판매 완료·생성 취소 묶음의 재활성화는 허용하지 않는다.
- 실사 뒤에는 이전 작업 정정·취소로 현재 수량을 덮어쓸 수 없다. 이후 작업은 실사 반영 수량을 기준으로 한다.

### OrchidGroupLineage

분갈이·분주·합식·자리 이동처럼 난 묶음 구성이 바뀌는 작업의 계보다.

- 복수 원본 구조 변경은 저장된 실행 회차를 중심으로 원본 목록·총 투입 수량·결과 목록·총 결과 수량·손실을 조회한다.
- 단일 원본 또는 기존 이력의 유효한 직접 연결은 `OrchidGroupLineage`로 호환 조회한다.
- 실제 원본 난 묶음은 전량 작업 시 수량 0·`종료` 상태로 보존하고, 작업 당시 값은 대상·효과 스냅샷으로 별도 보존한다.
- 같은 품종이지만 화분 크기·년생·상태가 다른 원본을 합칠 때 결과 속성을 결정하는 정책은 후속 결정 사항이다. 현재 결과 속성 기준 원본을 유지하며 이번 풀 수량 변경에서 속성 정책은 변경하지 않는다.

## 3. 거래처·판매 도메인

```text
BusinessPartner 1 ─ N SalesSlip 1 ─ N SalesSlipItem 1 ─ N SalesSlipItemAllocation
                                                    └─ N SalesOrchidGroupSnapshot
```

### BusinessPartner

거래처다.

- 일반 도매상
- 소매상
- 경매장

경매장도 거래처로 관리하되, 정산 설정과 경매 lot 연결이 필요하다.

### SalesSlip

판매 전표다.

- 일반 판매와 경매 판매를 구분할 수 있다.
- 판매일, 거래처, 입금 상태, 판매 상태, 총액, 메모를 가진다.
- A5 출력 대상이다.

일반 판매의 조건·가격·거래금액은 Direct 전용 모델이 소유한다. 실제 수납액은 Payment 유효 배분의 합계이며, 전표·품목의 금액 칼럼은 검색·분석과 호환 표시를 위한 projection이다. 생성·수정은 Direct가 계산한 금액을 같은 transaction에서 저장하고, 입금 후에는 유효 배분으로 요약을 갱신한다. 이전 대사의 원문과 전환 시점 불일치 근거는 현재 금액 원천과 구분해 보존하며 검토가 끝나기 전 새 입금·금액 변경을 차단한다.

### SalesSlipItem

판매 품목이다.

- 품목명/품종명
- 속명
- 규격
- 수량
- 단가
- 금액
- 하나 이상의 난 묶음 배분과 연결된다.

### SalesSlipItemAllocation

판매 품목과 난 묶음 사이의 배분 연결이다.

- 하나의 판매 품목은 여러 난 묶음에 나눠 배분할 수 있다.
- 배분 수량 합계는 품목 수량과 같아야 한다.
- 판매 품목의 품종명과 난 묶음 품종명이 일치해야 한다.
- 전표 저장 시 배분 수량만큼 난 묶음 `reservedQuantity`를 증가시킨다.

### SalesOrchidGroupSnapshot

판매 allocation에 배분된 난 묶음의 분석용 불변 스냅샷이다.

- `CREATION`은 전표 저장에서 예약 수량을 반영하기 전의 품종·수량·상태·위치를 보존한다.
- `OUTBOUND`는 출고·출하 완료에서 난 묶음을 잠그고 실제 수량을 차감하기 전의 값을 보존한다.
- 신규 스냅샷은 `LIVE`, migration으로 복원한 기존 자료는 `MIGRATED_CURRENT_STATE`로 구분해 과거 시점의 정확한 값으로 오인하지 않는다.

### SalesInventoryMovement

판매 전표로 인한 예약/해제/출고 이력이다.

- `SALES_RESERVE`
- `SALES_RELEASE`
- `SALES_OUTBOUND`
- `SALES_CANCEL_RESERVE`
- `SALES_CANCEL_OUTBOUND`

전표 저장 시점에 바로 재고 차감하지 않는다. 전표 저장은 예약만 반영하고, 실제 수량 차감은 출고·출하 완료 시점에 처리한다. 작성중 전표 수정도 기존 예약 해제와 새 예약을 각각 이력으로 남긴다.

## 4. 경매 추적 도메인

```text
AuctionShipmentLot
 ├─ AuctionAttempt
 │   └─ AuctionResultLine
 └─ AuctionLotStatusHistory

AuctionProceeds
 └─ 원본 AuctionResultLine 연결
```

### AuctionShipmentLot

경매장에 출하된 물건의 추적 단위다.

- 출하일
- 경매장
- 품목/품종/등급
- 출하 수량
- 판매 수량
- 대기 수량
- 반환 수량
- 현재 상태

후속 결정은 유찰 잔량 전체에 하나의 방법을 선택하며 결정 당시 수량을 이력으로 보존한다. 농장 반환 결정과 실제 도착은 별개이며 부분 도착을 허용한다. 새 흐름의 물량 요약은 `출하 = 판매 + 대기 + 실제 반환 + 경매장 처리`를 유지하며 반환 추정은 보조 상태로 분리한다. 실제 도착은 새 묶음·생성 Mutation, 취소 정정은 원래 도착·보상 Mutation을 연결한다. 유효한 도착 기록을 모두 정정하기 전에는 처리 결정을 바꾸지 않는다. 기존 반환 요약을 도착 이력이나 Farm 재고로 자동 변환하지 않는다.

### AuctionAttempt

경매 시도 이력이다.

- 같은 lot이 유찰 후 여러 번 경매될 수 있다.
- 경매일, 차수, 결과 상태를 기록한다.

### AuctionResultLine

경매 결과 원본 행이다.

- 같은 lot이 여러 단가로 나뉘어 판매될 수 있으므로 결과 행은 별도로 보존한다.
- 결과에 표기된 등급은 경매장 원본 결과와 lot의 매칭 분석을 위한 정보이며 출하 등급과 구별한다. 미입력 값은 미상으로 보존하고 출하 등급으로 추정하지 않는다.

### AuctionLotStatusHistory

상태 변경 이력이다.

- 출하, 유찰, 재경매 대기, 판매, 반환, 수량 보정 등을 기록한다.
- 추정/수동확인 여부를 남긴다.

### AuctionProceeds

경매장이 제공한 대금 자료와 원본 경매 결과 연결을 소유한다. 제공 낙찰액과 받을 금액은 미확인 상태를 유지할 수 있으며 자료 연결·금액 확인이 완료된 경우에만 새 입금을 허용한다. 실제 입금액은 Payment 유효 배분 합계다. 파생 정산 모델은 제거하며 원래 지급액·수수료를 추정하거나 파생 요약을 지급 근거로 복사하지 않는다.

## 5. 입금·잔액 도메인

```text
PartnerSettlementSettings
PartnerPaymentEvent
PartnerBalanceSummary
```

### PartnerSettlementSettings

거래처별 정산 규칙이다.

- 정산 단위
- 결제 지연일
- 결제일 모드
- 허용 오차
- 계좌/입금자명 매칭 설정
- 자동 정산/자동 매칭 사용 여부

### PartnerPaymentEvent

입금 이벤트다.

- 현재 공개 API는 일반 판매 전표 입금과 경매 대금 입금을 지원한다.
- 부분입금은 지원하고 잔액 초과 입금은 거부한다.
- 수동 입금 요청 키는 `externalUid`에 대상과 함께 저장해 같은 요청의 중복 반영을 막는다.
- 대상 미지정 수납은 실제 현금 원본과 미배분 금액을 보존한다. 새 배분은 원본 수납을 부모로 연결하며 여러 대상·여러 수납 조합을 지원한다.
- 배분 정정은 기존 연결을 취소 상태로 남기고 연결 해제 증거를 추가한다. 수납의 사용 가능액을 복구하고 필요하면 같은 트랜잭션에서 다시 배분한다. 유효 배분 합계만 대상 수납액에 반영하며 원래 수납액·입금일·식별자는 유지한다.
- 수납과 배분의 수지가 맞지 않거나 대상 소유권이 다르면 검토가 필요하다. 완료 명령 접수는 최초 결과 이벤트 ID를 보존해 재전송의 중복 반영을 막는다.
- 대상 미지정 수납의 오입력 취소와 실제 환불은 별개다. 예치금 전환·사용과 실제 환불은 아직 제공하지 않는다.

입금 처리는 삭제보다 이벤트 보존을 우선한다.

## 6. 운영 변경 감사

### AuditEvent

주요 운영 데이터의 변경 맥락을 원본 도메인 이력과 별도로 보존하는 이벤트다.

- 행위, 발생 원천, 대상 유형·ID, 변경 필드와 변경 전·후 스냅샷을 저장한다.
- 동·물리 배드·논리 구역·품종 ID는 운영 분석을 위한 선택 맥락으로 보존한다.
- 인증 계정, 세션, 브라우저 인스턴스, HTTP 요청 식별자를 연결한다.
- 난 묶음 관리의 단건·일괄 수정은 배치 속성과 메모만 변경해도 감사한다. 메모는 변경 필드명만 남기고 전후 원문을 감사 스냅샷에 복제하지 않는다. 원본 메모와 Mutation의 업무 사실 보존 정책은 유지한다.
- 일반·경매 전표 최초 생성은 예약·출고/출하 처리 후의 최종 전표 상태를 `CREATED`로 감사한다. 생성 요청 재전송은 새 감사를 만들거나 최초 실행자를 바꾸지 않는다. HTTP 맥락 없는 내부 호출의 인증 계정은 추정하지 않는다.
- 동일 값 변경은 이벤트를 만들지 않는다.
- 감사 저장은 원본 변경과 같은 트랜잭션에서 처리하며, 저장 실패 시 원본 변경도 롤백한다.
- 현재 별도 조회 API와 화면은 없으며 `audit_events`와 운영 분석 SQL로 확인한다.
- 거래처 개인정보와 입금자명·메모는 감사 스냅샷에 중복 저장하지 않는다.

# Domain Rules for Codex

이 문서는 코드와 OpenAPI만 보고는 놓치기 쉬운 도메인 의도와 운영 규칙만 기록한다.  
필드 타입, request/response schema, enum 전체 목록은 `openapi.yaml` 또는 실제 코드를 확인한다.

## 1. 문서 작성 원칙

- 코드에서 확인 가능한 Controller, DTO 필드, required 여부는 이 문서에 중복하지 않는다.
- API가 실제 구현되어 있는지는 `openapi.yaml` 또는 Controller 코드를 기준으로 판단한다.
- 이 문서는 구현 의도, 예외 정책, 운영상 금지 사항을 남기는 용도다.
- 과거 API 초안에 있으나 OpenAPI에 없는 endpoint는 제안/미구현으로 취급한다.

## 2. 공통 API 규칙

- Base URL은 `/api`다.
- 성공 응답은 `data`와 `message`를 갖는 공통 래퍼 형태를 사용한다.
- 에러 응답은 `error.code`, `error.message`, `error.details` 구조를 기준으로 한다.
- 요청/응답 날짜는 ISO-8601 날짜 문자열을 사용한다.
- 실제 응답 schema 이름은 OpenAPI의 `ApiResponse*` schema를 기준으로 확인한다.

## 3. 농장 구조/현황

- 농장 구조는 `house -> physical bed -> bed zone -> orchid group` 흐름으로 해석한다.
- 농장 현황 화면은 전체 조회 성격이다. 선택 대상이 동, 물리 배드, 논리 구역 중 무엇인지에 따라 포함되는 난 묶음 범위가 달라진다.
- 최근 작업 요약은 구조 API 자체의 책임으로 넣지 않고 작업 이력 API와 조합해서 표시한다.
- 줌 단계 API는 전체 농장 보기, 물리 배드 보기, 논리 구역 보기의 단계적 렌더링을 위한 데이터다.

## 4. 난 묶음

- 난 묶음 생성 위치는 논리 구역 기준이다.
- 난 묶음 관리의 삭제는 물리 삭제가 아닌 수량 0·`생성 취소` 상태 전환이다. 작업 연결이 모두 `CANCELED` 또는 `VOIDED`이면 이력을 보존한 채 허용한다. 계획·진행·완료·`STOPPED` 작업 연결, 판매·재고 이동·입고 연결, 예약 수량이 남아 있으면 차단한다.
- 난 묶음 생성·수정 시 품종은 자유 입력하지 않고 `varietyId`로 선택한다.
- 일반 난 묶음 생성·수정에서 `생성 취소` 상태를 직접 지정할 수 없다. 전용 취소 경로에서 수량 0과 원장·참조 검사를 함께 적용한다.
- 이미 생성 취소된 난 묶음의 일반 수정·재활성화도 금지한다.
- 화분 크기는 서버가 표준 코드로 정규화하며 임의 문자열 입력은 거부한다.
- 안전하게 해석할 수 없는 기존 화분 값은 `UNMAPPED`로 보존하고 자동 그룹에서 제외한다.
- 난 묶음 보정 API는 구역 이동을 담당하지 않는다. 단순 이동도 작업의 자리 이동 즉시 기록·구조 변경 실행으로 처리하며 일반 이동 전용 API는 제공하지 않는다.
- 난 묶음 일괄 보정은 선택 대상별 입력값을 한 트랜잭션에서 적용한다. 화면의 `개별값 유지` 필드는 각 난 묶음의 기존 값을 요청값으로 전달한다.
- 단건·일괄 보정은 대상 묶음 전체와 현재 구역 전체를 각각 ID 순으로 잠근 뒤 적용한다. 무변경 판단·감사의 변경 전 값도 대기 후 최신 상태를 기준으로 한다. 잠금 순서와 별개로 입력·응답 순서를 유지하며, 한 항목이라도 실패하면 앞선 변경·Mutation·감사를 함께 rollback한다.
- 묶음 관리의 단건·일괄 보정은 배치 속성·메모만 변경해도 감사한다. 메모는 변경 필드명만 남기고 감사 전후 스냅샷·맥락에 원문을 복제하지 않는다. 동일 값 보정은 Mutation·감사를 추가하지 않으며 감사 실패는 원본 변경도 rollback한다.
- 작업 결과 수량 보정은 최종 활성 묶음의 배치 범위·구역 내 표시 순서가 기존 묶음 또는 같은 요청의 다른 결과와 충돌하면 전체를 거부한다. 일반 상태 보정에 `생성 취소`를 지정할 수 없으며 전용 결과 생성 취소로만 수량 0·`CANCEL_CREATION`을 기록한다.
- 난 묶음 이동 단위는 기본적으로 묶음 전체다.
- 이동 성공 시 자리 이동 작업 이력이 자동 생성된다.
- 자리 이동 실행은 목적 구역과 시작·끝 위치를 명시한다. 명시적인 1:1 전량 이동은 기존 ID를 유지하며 `MOVE` 원장에 기록한다. 과거 일반 이동 이력의 조회·취소는 유지한다.
- 구역 내 정렬은 생성/이동 시 `sortOrder` 기준으로 관리한다. 수동 reorder API는 현재 OpenAPI에 없다.
- 구조 변경은 원본 난 묶음을 결과로 덮어쓰지 않고 별도 난 묶음과 계보 관계를 남긴다.
- 복수 원본 구조 변경 계보는 저장된 실행 회차를 중심으로 원본·결과 난 묶음, 관계 유형, 원인 작업, 작업 당시 수량을 보존한다.
- 난 묶음 계보 조회의 `transformations`는 실행 회차별 원본·결과를 반환하고 `sources`·`results`는 단일 원본 및 기존 직접 계보 호환 필드다.

## 4-1. 난 묶음 사용자 그룹

- 사용자 그룹 소속은 난 묶음의 위치·속성·상태 변경과 독립적으로 유지한다.
- 작업·포트 취소도 구성원을 자동 해제하지 않으며 기존 소속 이력을 보존한다.
- 하나의 난 묶음은 여러 사용자 그룹에 동시에 속할 수 있다.
- 구성원 해제는 삭제 대신 해제 시각을 남기고, 같은 활성 소속의 중복 추가는 한 건으로 유지한다.
- 사용자 그룹은 삭제 대신 `ARCHIVED`로 보관하며 보관 후 구성원을 추가하거나 해제할 수 없다.
- 기본 목록은 활성 그룹만 반환하고 `includeArchived=true`일 때 보관 그룹을 포함한다.

## 4-2. 난 묶음 자동 그룹

- 자동 그룹은 `varietyId + 현재 ageYear + potSizeCode`로 조회 시 계산하며 별도 저장하지 않는다.
- 수량 0, 종료·폐기·판매 완료 상태, `UNMAPPED` 화분 값은 자동 그룹에서 제외한다.
- 년생 미지정 그룹 키는 `UNSPECIFIED` 토큰을 사용한다.
- 그룹 키는 영구 식별자가 아니므로 구성원 조회 시 현재 속성에 맞는 난 묶음만 반환한다.
- 난 묶음 속성 변경 직후 다음 조회 결과와 그룹별 총수량이 달라질 수 있다.

## 5. 배드 정밀 배치

- 배치 프로필은 논리 구역의 구간과 규격, 화분 크기, 배치 모드별 수용량을 표현한다.
- 실제 배치가 존재하는 구간은 삭제하면 안 된다.
- 정밀 배치의 향후 확장은 공통 자리 이동 실행 계약을 기준으로 검토하며 별도 일반 이동 API를 재도입하지 않는다.
- 수용량이 변경되어 추천 당시 조건과 달라진 경우 `CAPACITY_CONFLICT` 계열 충돌로 처리한다.
- 신규 자리 이동은 배치 구간을 명시하며 기존 구간 미지정 일반 이동 요청은 제공하지 않는다.

## 6. 작업 이력/작업 유형

- 작업 이력은 삭제보다 보존을 우선한다.
- 실수로 생성한 작업 이력은 삭제하지 않고 취소 상태로 전환한다.
- 완료된 구조 변경이나 독립 폐기를 현실에서 수행하지 않은 것으로 확인한 경우에는 `VOIDED`로
  무효화한다. 원본 이력은 보존하고 SOURCE 복원과 모든 RESULT 생성 취소를 `COMPENSATION`
  Mutation으로 기록한다. 실제 현장에서 수행한 폐기를 되돌리는 용도로 사용하지 않는다.
- 구조 변경·폐기 무효화는 모든 관련 난 묶음에 상쇄되지 않은 후속 Mutation과 외부 참조가 없을 때만
  허용한다. 후속 구조 변경이 이미 보상되었다면 이전 작업도 순서대로 무효화할 수 있으며, 같은 원본
  Mutation을 두 번 무효화할 수 없다.
- 완료된 구조 변경·이동·폐기의 연속 효과는 일괄 취소할 수 있다. 명시한 원본 난 묶음은 과거 위치로 복구하지 않고 바로 생성 취소하며, 명시하지 않은 원본은 기존 복원 검사를 유지한다. 복구 대상끼리 또는 남은 활성 묶음과 배치 범위·구역 내 표시 순서가 충돌하면 전체를 거부한다. 이동에 연관 폐기가 있으면 함께 선택해야 한다. 선택 범위 밖의 유효 작업·판매·입고 참조와 예약, 후속 변경은 차단한다. 작업·효과 취소와 하나의 보상 Mutation·감사 기록은 원자적으로 처리한다. 같은 키의 내용 변경은 거부한다.
- `RECONCILIATION` 현장 상태 동기화는 정책 재검토를 위해 보류한다. 기존 작업과 Mutation은 보존하지만
  화면 진입과 신규 API 실행은 비활성화한다.
- 취소된 작업 이력은 기본 조회, 최근 작업, 통계 집계에서 제외한다.
- 작업 취소 가능 조회에는 복구 배치·표시 순서 충돌도 차단 사유로 반환한다. 일괄 취소에서 선택 이력 사이의 구간은 실제로 보상된 Mutation 쌍과 연속 snapshot을 확인한 경우에만 건너뛸 수 있다.
- 단건 취소는 일괄 취소와 동일하게 `STOPPED` 작업 참조를 차단하며 같은 멱등 키의 사유 변경은 `409 IDEMPOTENCY_KEY_REUSED`로 거부한다. DB 잠금·버전 충돌은 공통 `409 CONCURRENT_MODIFICATION`으로 응답한다.
- 입고 화면의 포트 취소는 부분 실행 작업도 전체 보상한다. 입고별 같은 키·사유 재요청은 기존 접수를 재사용하므로 이후 재포트 작업에 영향을 주지 않는다.
- `STOPPED` 포트 작업의 적용 결과는 보존하며 해당 배치 완료 입고의 취소 action은 제공하지 않는다. 입고 수정·취소·포트 취소는 잠금 후 최신 상태를 검증하여 동시 요청이 상태를 덮어쓰지 않게 한다.
- 작업 대상 선택 이후 취소·변경이 먼저 완료된 경우 등록은 `409 WORK_TARGET_CHANGED`로 거절한다. 현재 대상을 다시 조회하여 선택해야 한다.
- 작업 이력 수정/삭제 API는 현재 OpenAPI에 없다. 구현 전에는 존재한다고 가정하지 않는다.
- 작업 유형은 seed 기본 유형과 사용자 커스텀 유형을 함께 사용한다.
- 비활성 작업 유형은 기존 이력 조회에는 남아야 하지만 일반 작업 기록 생성에는 사용할 수 없다.
- 시스템 작업 유형, 특히 자리 이동 계열은 일반 생성 폼에서 선택하지 않는다.
- 입고 유형은 입고 관리 흐름에서 자동 생성한다. 포트 작업 기록은 포트 대기 입고 기록을 대상으로 모든 결과를 입력해 등록하며, 입고 관리의 즉시 포트 작업도 완료된 `WorkOperation`으로 기록한다.
- 신규 입고 등록 이력은 입고 기록 대상을 가진 완료된 `WorkOperation`으로 저장한다.
- 같은 입고 기록은 활성 포트 작업 계획에 중복 포함할 수 없다. 입고 관리에서 즉시 실행할 때 활성 계획이 있으면 새 작업을 만들지 않고 기존 계획의 해당 대상을 실행한다.
- 활성 포트 작업의 미완료 대상은 연결된 입고 기록의 최신 정보를 표시한다. 실행 직전에 최신 정보를 스냅샷으로 확정하고 완료 후에는 원본 변경을 전파하지 않는다. 원본을 조회할 수 없으면 기존 스냅샷을 사용한다.
- 유리병 모종은 포트 예정일 유무와 관계없이 `POTTING_PENDING`으로 관리한다. 임시 보관 여부와 위치는 상태가 아닌 `tempLocation`으로 표현한다. 포트 작업 계획을 생성하면 대상 입고 기록은 `POTTING_IN_PROGRESS`가 되고, 작업을 취소하거나 대상을 건너뛰면 `POTTING_PENDING`으로 복귀한다. 결과 난 묶음이 없는 입고 기록을 취소하면 연결된 입고 작업과 해당 입고 기록의 미완료 포트 작업 대상도 함께 취소한다. 여러 입고 기록을 묶은 포트 작업은 다른 대상까지 취소하지 않는다.
- 포트 작업 결과는 하나 이상의 난 묶음이며 각 결과는 수량·화분·년생·배치 규격·논리 구역을 독립적으로 가진다. 입고 Entity에 결과 속성이나 대표 난 묶음을 중복 저장하지 않고, 작업 효과와 `OrchidGroup.inboundRecord`로 전체 결과를 추적한다.
- 자리 이동·분갈이·분주·합식·포트 작업은 작업 하나당 한 품종으로 제한한다. 화면의 혼합 품종 선택은 계획과 즉시 기록 모두 품종별 독립 작업으로 분리한다.
- 작업 유형 템플릿은 입력 필드와 목록/상세 표시값을 결정한다.
- 작업 이력의 공통 검색 필드는 정형 컬럼으로 유지하고, 작업별 가변 정보는 `details`에 보관한다.
- 완료 작업 상세 화면은 JSON 저장값을 직접 해석하지 않고 정형 상세 API를 사용한다. 상세 API는 `WorkAppliedEffect`의 모든 실행 회차를 순서대로 반환하며, 과거 기록에 저장되지 않은 값을 현재 난 묶음 상태로 추정하지 않는다.
- 신규 `WorkOperation`은 상위 범위를 저장할 때 실제 난 묶음 대상과 당시 위치·속성·수량을 확정한다.
- 상위 작업은 난 묶음별 이력 행으로 복제하지 않고 대상 연결을 통해 하위 이력에 표시한다.
- 동·물리 배드·논리 구역·난 묶음 범위 이력 조회는 범위 안 난 묶음의 직접·전파 이력을 서버에서 통합하고 작업 ID 기준으로 중복 제거한다.
- 통합 작업 이력은 0부터 시작하는 서버 페이지네이션을 사용하며 페이지 크기는 최대 100이다.
- 구형 난 묶음 작업 이력은 작업일·ID 내림차순 최신 500개 작업까지만 반환한다. 전체 과거 이력은 통합 페이지 조회를 사용한다.
- 작업 캘린더는 양 끝 날짜를 포함해 366일 이내, 최대 1,000개 작업의 완전한 목록을 반환한다. 기간 초과는 400, 결과 상한 초과는 422 `QUERY_LIMIT_EXCEEDED`이며 일부 작업을 성공 응답으로 반환하지 않는다. 기간·필터를 좁히거나 작업 목록의 페이지 조회를 사용한다.
- Work/Mutation 그래프는 부분 조회다. 노드/깊이뿐 아니라 내부 대상·효과·정정 또는 관계 상한으로 생략한 경우도 `truncated=true`다. 그래프에서 보이지 않는 과거 이력이나 관계가 없다고 판단하지 않는다.
- 작업 관리 목록도 0부터 시작하는 서버 페이지네이션을 사용한다. `size`는 기본 20, 최대 100이며 키워드는 작업명·작업 유형명/코드·작업자·메모를 검색한다.
- 기간 작업 대상 선택은 동 전체, 자동 그룹 키, 활성 사용자 그룹, 직접 난 묶음 ID 목록을 지원한다.
- 즉시 완료 기록형 작업은 농장 전체, 동, 물리 배드, 논리 구역, 난 묶음 범위를 지원한다.
- 사용자 그룹에서는 현재 작업 가능한 구성원만 대상이 되고, 직접 선택에 작업 불가능한 난 묶음이 섞이면 요청을 거부한다.
- 자동 그룹과 사용자 그룹 구성이 저장 후 바뀌어도 확정된 작업 대상 스냅샷은 변경하지 않는다.
- 일반 기록형 작업과 자리 이동·분갈이·분주·합식·폐기는 난 묶음 대상 기간 작업으로 계획할 수 있다. 입고 포트 작업은 입고 기록 대상을 별도로 확정한다.
- 분갈이·분주·합식 작업 기록은 선택한 원본을 품종별 작업으로 나누고, 각 작업의 계획 수량 전체와 모든 결과를 하나의 배치 요청으로 처리하며 부분 실행 회차를 만들지 않는다.
- 신규 구조 변경 단건·일괄 기록은 Receipt 확인 후 전체 원본과 현재·결과 구역을 각각 ID 순으로 잠근 뒤 계획을 생성한다. 대기 후 원본 수량이 입력과 달라졌거나 계획 대상이 실행 원본과 다르면 전체를 거절한다. 처리·응답 순서와 같은 배치의 해제 위치 재사용 정책을 유지하며, 후행 기록 실패는 Receipt·작업·효과·Mutation·계보·감사를 함께 rollback한다. 완료된 Receipt 재전송에는 이 선잠금·현재 상태 validation을 다시 적용하지 않는다.
- 폐기 작업 기록은 선택한 모든 대상의 폐기 수량을 한 번씩 입력해야 하고, 포트 작업 기록은 선택한 모든 입고 기록의 결과를 입력한 뒤 품종별 완료 작업으로 저장한다.
- 일반 품종별 일괄 계획·폐기 기록은 제외 대상을 뺀 전체 묶음 잠금을 ID 순으로 취득한 뒤 품종별 작업을 만든다. 대기 중 해석한 대상의 version이 변경되면 기존 `WORK_TARGET_CHANGED`로 전체 요청을 거절한다. 후행 폐기 실패 시 앞선 계획·실행·효과·Mutation·감사까지 롤백하며 키 없는 기록의 재전송 멱등성은 보장하지 않는다.
- 기간 작업 실행과 완료는 농장 기준 실제 완료일을 저장한다. 완료일은 오늘이 기본이며 오늘 이후 날짜는 허용하지 않는다.
- 전체 작업 완료는 대상이 한 건 이상이고 모든 대상 실행이 `COMPLETED`, `SKIPPED`, `CANCELED` 중 하나일 때만 허용한다. 대상 취소는 효과를 실행한 완료와 구분하지만 전체 완료 검사에서는 닫힌 대상으로 취급한다. `PENDING`, `IN_PROGRESS`, `PARTIALLY_COMPLETED`, `FAILED`가 남으면 완료할 수 없다. 대상 실행/건너뜀 이후 자동 완료는 전체 작업이 `IN_PROGRESS`일 때만 적용한다. 전체 작업 취소·`STOPPED` 처리 자체를 자동 완료로 바꾸지 않는다.
- `남은 작업 종료`는 이미 완료된 대상과 적용된 효과·이력을 보존하고, 미완료 대상과 부분 완료 대상의 잔여 수량만 닫은 뒤 `STOPPED`로 전환한다.
- `작업 취소`는 등록 가능한 일반 기록형과 구조 변경형 작업에 공통으로 적용한다. 부분 실행 작업은 미완료 대상을 닫고 기록 효과를 취소하며, Mutation이 있으면 후속 참조를 검증한 뒤 모두 보상한다. 원본 기록과 Mutation은 삭제하지 않는다.
- 작업 목록의 `status=CANCELED`는 사용자에게 취소로 표시하는 내부 `CANCELED`와 `VOIDED`를 함께 조회한다. 완료 효과를 유지한 `STOPPED`는 별도 상태로 조회한다.
- `CANCELED`와 `VOIDED` 작업은 적용 효과가 취소·보상되었으므로 목록과 상세의 진행률을 0%로 제공한다. `STOPPED`는 완료 효과를 유지하므로 기존 진행률을 유지한다.
- 자리 이동 계획은 생성 시 위치를 바꾸지 않는다. 실행·즉시 기록 시 같은 품종의 원본 투입 수량과 한 개 이상의 이동 결과 및 유효한 배치를 검증해 이동 효과를 적용한다. 작업으로 비워지는 원본 배치는 이동 결과 위치로 다시 사용할 수 있다.
- 모든 결과의 `attributeSourceOrchidGroupId`가 원본과 중복 없는 1:1로 대응하고, 각 원본 전량과 결과 수량이 같으며 위치만 바뀌면 기존 난 묶음 ID와 속성을 유지한 채 하나의 `MOVE` Mutation으로 이동한다. 이 경우 새 난 묶음과 `MOVED_TO` 계보를 만들지 않는다.
- 동일 조건을 만족하는 과거 `TRANSFORM` 이동 이력도 원본 ID를 유지하는 `MOVE` 상태 체인으로 이관한다. 이관된 결과 ID의 후속 참조는 원본 ID로 통합하고 제거 ID 대응과 snapshot은 감사 테이블에 보존한다. 과거 실행기가 결과 생성 시 메모·입고 출처 같은 원본 전용 속성을 누락했더라도 후속 Mutation이 없고 핵심 품종·수량·상태가 같으면 원본 속성을 복원한다. 대응이 불명확하거나 업무 속성이 실제로 변경된 이력은 자동 이관하지 않는다.
- 그 외 같은 품종의 여러 원본과 여러 결과는 `MOVED_TO` 실행 회차에 각각 연결하며 결과별 직접 원본 수량을 만들지 않는다. 상태가 좋은 수량을 먼저 이동하고, 전체 선별 수량과 이동 결과 수량의 차이는 원래 자리에 남은 수량으로 보고 원본별 선별 수량 비율로 자동 배분하여 폐기한다. 이동과 폐기는 같은 트랜잭션에서 처리하고 정수 나머지는 최대 나머지 방식으로 배분하며 동률은 난 묶음 ID 오름차순으로 해소한다. 폐기 작업은 `MOVEMENT_DISCARD` 관계로 원본 자리 이동 작업을 직접 참조하며 배분 방식과 총 폐기 수량을 작업 상세에 보존한다.
- 분갈이·입고 포트 계획은 생성 시 구조를 바꾸지 않고 대상별 완료 시 결과 입력을 검증한 뒤 구조 변경 효과를 적용한다.
- 자리 이동·분갈이·분주·합식은 실제 원본 N개와 결과 M개를 허용하고 작업 유형에 따라 `MOVED_TO`, `REPOTTED_TO`, `SPLIT_TO`, `MERGED_TO` 계보를 기록한다. 합식의 원본은 하나 이상이면 된다. 분갈이와 분주는 결과 수량이 투입 수량보다 클 수 있으며 차이를 증식 수량으로 기록한다. 자리 이동과 합식은 결과·손실 수량 합계가 투입 수량과 같아야 한다.
- 구조 변경 요청에는 손실 수량과 손실 사유를 받지 않는다. 서버는 `max(0, 투입 수량 합계 - 결과 수량 합계)`를 손실 수량으로 자동 저장한다.
- 구조 변경은 여러 실행 회차에서 계획 수량 일부를 처리할 수 있으며 누적 작업 수량과 잔여 수량을 보존한다.
- 폐기 수량은 현재 가용 수량을 초과할 수 없다. 일부 폐기는 난 묶음의 기존 상태를 유지하고, 전량 폐기는 수량 0·`폐기` 상태로 전환한다.
- 결과의 `DIVIDE_CANDIDATE`와 `HELD` 구분은 각각 분주 예정과 별도 보관 상태로 생성하되 자동 그룹 계산과 계보 조회 대상에서 제외하지 않는다.
- 사용자 수동 입력과 직접 이동을 포함한 모든 신규 운영 이력은 `WorkOperation`으로 기록한다.
- 대상별 처리는 전체 작업이 `IN_PROGRESS`일 때만 가능하고 `PAUSED`에서는 금지한다.
- 대상 완료는 작업 효과 handler 실행, 효과 감사 기록, 대상 완료 상태 변경을 같은 트랜잭션에서 처리한다.
- 완료 요청을 재시도해도 이미 적용된 효과와 최초 작업자·결과 상세를 변경하지 않는다.
- 다중 난 묶음 생성은 원본 대상 없이 완료된 작업으로 기록하며 생성 결과를 작업 효과에 연결한다.
- 키가 있는 즉시 실행·구조 변경 기록·포트 기록은 같은 범위·키·요청 내용일 때 저장한 작업 ID를 재사용한다. 같은 키의 내용 변경은 409 `IDEMPOTENCY_KEY_REUSED`로 거절한다. 완료된 회차도 이 규칙을 적용한다.
- 일반 단건·일괄 계획과 일반 완료 기록 생성은 선택형 `Idempotency-Key` header로 재전송을 식별하며 경로별 키 범위가 독립적이다. 같은 경로·키·입력은 최초 응답을 201로 반환하고 변경 입력은 409 `IDEMPOTENCY_KEY_REUSED`다. 키 없는 생성은 별도 작업이며 재전송은 경로와 입력도 유지한다. 현재 작업명·상태·대상으로 최초 응답을 덮어쓰지 않는다.
- 일반 생성의 전체 품종별 작업·대상·실행·효과·기존 감사와 Receipt의 지문·결과 ID·응답 snapshot·생성 membership은 한 트랜잭션에 확정/rollback한다. 기존 실행·구조 변경·포트 Receipt의 현재 상세 재조회 계약과 과거 미상 응답은 유지한다.
- 원문이 없는 과거 즉시 요청의 재실행은 409 `IDEMPOTENCY_REPLAY_UNAVAILABLE`이며 이력 조회는 유지한다. 키 없는 계획·일반 기록 API에는 이 보장을 적용하지 않는다.
- 포트 작업 기록의 각 실행은 `idempotencyKey`가 필수다. 같은 입고 기록에서 같은 키와 같은 실행 내용을 재요청하면 기존 작업 결과를 반환하고, 다른 실행 내용으로 키를 재사용하면 거부한다.
- 취소되지 않은 작업 또는 판매·재고 이동·입고 참조와 예약 수량이 남아 있으면 생성 취소를 차단한다. 취소된 작업 이력만 남아 있거나 같은 일괄 취소에서 함께 무효화하는 작업의 참조는 이력을 보존한 채 허용한다.
- 단건 삭제 요청은 난 묶음을 물리 삭제하지 않고 수량 0과 `생성 취소` 상태로 전환한다. 기존 작업 참조 등 변경 금지 조건은 유지한다.
- 분갈이 투입 수량은 결과 수량 합계와 손실 수량의 합과 같아야 하며, 투입 수량만큼 원본에서 차감한다.
- 원본 수량 전체를 투입하면 원본은 수량 0·`종료` 상태가 되고, 일부만 투입하면 잔여 수량으로 활성 상태를 유지한다.
- 분갈이 결과는 원본 품종과 상태를 이어받고 새 위치·년생·화분 크기를 가지며 `REPOTTED_TO` 계보로 연결한다.
- 손실 수량이 있으면 손실 사유가 필수다. 결과에 상속할 사용자 그룹은 원본의 활성 소속 중에서 명시적으로 선택한다.
- 완료된 구조 변경 작업의 정정은 원본에 속한 감사 이벤트로 저장한다. 독립 작업·작업 효과를 생성하지 않는다.
- 보정 후에도 원본 작업은 완료 상태를 유지하며 실행 당시 결과 스냅샷을 보존한다. 보정 건수와 보정 가능 여부는 서버 계약으로 제공한다.
- 보정 효과는 원본 구조 변경 작업의 작업일과 해당 작업이 만든 결과 난 묶음의 수량·상태만 변경할 수 있다. 다른 난 묶음은 보정 대상으로 지정할 수 없다.
- 후속 작업·이동 이력·판매·재고 이동·입고가 연결된 결과는 보정을 차단하고, 보정 수량은 현재 예약 수량보다 작을 수 없다.
- 보정 전후 작업일·수량·상태와 사유는 보정 이벤트에 보존한다. 날짜만 변경하면 난 묶음 Mutation을 만들지 않는다. 새 난 묶음 생성이나 계보 교체는 아직 보정 효과 범위가 아니다.
- 작업 기록의 수량 정정과 실사 수량 조정은 현재 기본 비활성화하며 신규 변경 요청은 `409 FEATURE_ON_HOLD`로 거부한다. 수량 수지 선언 없는 기존 payload도 결과 수량을 바꾸면 차단한다. 작업일·상태 정정과 결과 생성 취소, 기존 감사 이력 조회 및 완료된 요청의 멱등 재조회는 유지한다.
- 비활성화된 작업 수량 정정 구현은 저장된 실행·감사 기록 기준으로 `투입 + 증식 = 결과 + 손실`을 검증한다. 결과 수량 변경은 수량 수지를 명시해야 하며, 손실·증식을 자동 추정하지 않는다. 투입량 정정은 원본 난 묶음 수량을 자동 변경하지 않으며, 증식은 분갈이·분주에서만 허용한다. 포트 입고 투입량과 이동 연관 폐기량은 결과 정정으로 변경하지 않는다.
- 실사 수량 조정은 현재 업무일·확인 revision을 기준으로 현재 수량만 변경하고 별도 작업을 생성하지 않는다. 수량 차이를 과거 손실·증식으로 자동 해석하지 않는다. 상태·위치·계보·과거 스냅샷을 보존하며, 예약 수량 침해·비활성 묶음·배치 충돌은 거부한다. 감사 기록과 Mutation은 같은 트랜잭션으로 멱등 처리한다.
- 실사 이후 이전 작업의 결과 보정·생성 취소·취소는 현재 실사 값을 덮어쓸 수 없다. 현재 수량과 작업의 마지막 정정 수량이 다른 경우에도 수량 수지 정정을 거부한다. 기존 다목적 `RECONCILIATION` 신규 실행은 계속 비활성화한다.
- 전체 완료 전 모든 대상은 `COMPLETED` 또는 `SKIPPED`여야 한다.
- 완료된 대상이 있는 전체 작업은 일반 취소할 수 없다.
- 난 묶음 이력은 `WorkOperationTarget`과 `WorkEffectOrchidGroup` 연결만 조회하며 V8에서 변환된 과거 이력도 `WorkOperation`으로 조회한다.

## 6-1. 품종/입고/자재

- 품종과 자재는 운영 데이터 보존을 위해 삭제보다 비활성화를 우선한다.
- 품종은 `속 + 품종명` 조합을 기준으로 식별하며, 같은 조합은 중복 등록할 수 없다.
- 품종 색상은 선택값이며 `#RRGGBB` 형식만 저장한다. 미지정 품종은 화면별 기본 색상 규칙을 사용한다.
- 품종 삭제는 연결된 난 묶음이나 입고 기록이 전혀 없을 때만 허용한다.
- 품종의 최근 작업일은 해당 품종의 현재 양수 난 묶음을 대상으로 한 완료 작업의 최신 업무일이다. 페이지의 다른 품종 작업일을 공유하지 않으며 제외 대상은 작업일 계산에서 제외한다. 연결 개수/전체 수량에는 양수 묶음의 상태와 관계없이 포함하고, 판매 가능량은 기존 상태 정책과 예약 잔량을 적용한다.
- 자재 삭제는 현재 연결 데이터가 없을 때만 허용한다.
- 품종, 자재, 입고 목록 API는 서버 페이지네이션을 사용한다. `page`는 0부터 시작하고 `size`는 기본 10, 최대 100이다.
- 입고는 `FLASK_SEEDLING`과 즉시 배치 계열이 입력 규칙과 후속 흐름이 다르다.
- 생성의 `Idempotency-Key`는 입고 생성 전체에서 유일하게 사용한다. 같은 키·입력은 최초 응답을 `201`로 재조회하고 다른 입력은 `409 / INBOUND_CREATE_REQUEST_KEY_CONFLICT`다. 키 생략은 기존의 독립 생성이며 실제 별도 입고에는 새 키를 사용한다. 판매 생성·Work 실행/취소 키와는 namespace를 공유하지 않는다.
- 생성 접수·신규 품종·입고·즉시 배치 Mutation/묶음·완료 Work/효과·감사는 한 트랜잭션에서 확정하거나 rollback한다. 실패한 요청은 키를 소비하지 않는다. 수정·취소·포트 이후에도 최초 응답을 유지하며 현재 위치·상태로 업무를 다시 실행하지 않는다.
- `FLASK_SEEDLING`은 포트 작업 전까지 `POTTING_PENDING`으로 관리하며, 임시 보관 위치와 포트 예정일은 선택 데이터다.
- 입고는 입고 사실과 포트 대기 정보만 소유한다. 병 수, 실제 수량, 화분, 년생, 생육 단계, 배치 규격, 트레이 수, 배치 구역, 포트 완료일은 입고 컬럼으로 중복 저장하지 않는다.
- 입고 기록은 난 묶음 생성·배치 완료 전(`POTTING_PENDING`, `POTTING_IN_PROGRESS`)에만 수정할 수 있다. 화면은 응답의 `editable`을 수정 가능 여부의 기준으로 사용한다.
- 완료된 포트 작업은 생성 난 묶음에 후속 변경이나 외부 참조가 없을 때 생성 Mutation을 보상하고, 값을 덮어쓰지 않은 기존 입고 기록을 `POTTING_PENDING`으로 다시 열어 무효화한다.
- 포트 작업의 작업자와 메모는 작업 이력이 소유하며, 포트 완료 처리로 입고 담당자와 입고 메모를 변경하지 않는다.
- 즉시 배치 입고는 `placement`에 난 묶음 결과를 받아 같은 트랜잭션에서 Mutation으로 생성한다.
- 난 묶음이 생성된 입고 기록은 생성 Mutation을 안전하게 보상할 수 있을 때만 취소할 수 있다.
- 입고 기록은 취소 여부와 관계없이 물리 삭제하지 않는다. 상태 조건이 없는 전체 목록에도 `CANCELED`를 포함하고, 명시적으로 `status=CANCELED`를 지정하면 취소 이력만 조회한다.
- 즉시 배치 입고 취소는 입고가 생성한 난 묶음의 생성 Mutation을 보상하고 연결 입고 작업을 `VOIDED`로 보존한다. 배치 완료 유리병 모종은 포트 작업만 무효화해 `POTTING_PENDING`으로 되돌리거나 포트 작업 보상 후 입고까지 `CANCELED`로 전환할 수 있다. 생성 난 묶음에 상쇄되지 않은 후속 변경이나 판매·다른 작업 참조가 있으면 거부한다.
- 자재 코드는 서버가 순번 기반으로 자동 발급한다.

## 7. 판매 전표

- 생성의 `Idempotency-Key`는 일반·경매 전표 생성 전체에서 같은 namespace를 사용한다. 같은 키·같은 입력은 최초 응답을 반환하고, 다른 입력은 `409 / SALES_CREATE_REQUEST_KEY_CONFLICT`다. 실제 별도 생성은 새 키를 사용한다. 키를 생략하면 기존처럼 매번 새 전표를 생성한다.
- 일반·경매 전표 최초 생성은 출고/출하까지 처리한 최종 전표 상태를 `CREATED`로 감사한다. 같은 생성 요청의 replay는 감사와 최초 실행자를 변경하지 않는다. 키 없는 별도 생성은 각각 감사하며, HTTP 맥락 없는 내부 호출의 인증 계정은 추정하지 않는다.
- 접수는 전표·예약·출고/출하·snapshot·Mutation·잔액·감사와 함께 확정하거나 rollback하며, 실패한 요청은 키를 소비하지 않는다. replay는 최신 거래처·재고·전표 상태 검증 전에 최초 응답을 반환한다. 기존 전표를 수정·취소해도 생성 응답을 덮어쓰지 않는다.
- 판매 전표 품목 금액은 `quantity * unitPrice`로 계산한다.
- 전표 `totalAmount`는 품목 금액 합계로 계산한다.
- 품목 금액 또는 전표 합계가 2,147,483,647원을 넘으면 생성·수정을 `400 / VALIDATION_ERROR`로 거절한다. 예약·Mutation·이동 이력·잔액·감사를 포함한 해당 변경은 rollback하며, 금액을 잘라 저장하거나 0원으로 보정하지 않는다. 0원 단가는 허용한다.
- 현재 세금 구분 계약은 없으므로 `totalAmount`에서 공급가액·부가세를 임의 계산하지 않는다.
- 전표 번호는 판매일 기준 순번으로 자동 생성한다. 같은 판매일의 동시 생성은 일별 카운터 행에서 직렬화해 중복 번호를 만들지 않는다.
- 판매 전표 품목은 하나 이상의 난 묶음 allocation을 가져야 한다.
- allocation 합계는 판매 품목 수량과 같아야 한다.
- allocation 대상 난 묶음의 품종은 판매 품목명과 같아야 한다.
- 전표 저장 시 난 묶음 `reservedQuantity`를 증가시킨다.
- 판매 선택 조회와 신규 예약은 판매 가능 수량 집계와 같은 Farm 상태 정책을 사용한다. 판매 불가 상태는 상태 필터를 지정해도 선택할 수 없으며, ID를 직접 지정한 생성·수정 재예약도 `400 / VALIDATION_ERROR`로 거절하고 전체 변경을 rollback한다.
- 예약 이후 판매 불가 상태가 되어도 기존 예약 해제·출고·취소 복구는 현재 예약 수지로 처리한다. 이미 적용한 예약 Mutation의 같은 키·내용 재요청은 새 예약이 아니므로 기존 결과를 반환한다. 판매 불가 묶음에 새 예약을 남기지 않는 다른 묶음으로의 배분 변경은 허용한다.
- allocation 생성은 예약 반영 전 난 묶음을 `CREATION` 스냅샷으로, 출고·출하 완료는 난 묶음 잠금 후 재고 차감 전 값을 `OUTBOUND` 스냅샷으로 보존한다.
- migration으로 생성한 기존 전표 스냅샷은 과거 시점의 정확한 값이 아닌 현재 상태 복원값이므로 source로 구분한다.
- 난 묶음 변경은 `0 <= reservedQuantity <= quantity`를 유지해야 하며, 판매 예약·해제·출고는 관련 난 묶음을 ID 순서로 잠근 뒤 처리한다.
- `PUT /api/sales-slips/{salesSlipId}`는 `작성중` 일반 판매 전표만 수정할 수 있다.
- 현재 수정은 기존 품목 개수를 유지하는 경우만 지원한다.
- 수정 시 기존 예약 해제와 새 예약을 재고 이동 이력으로 각각 남기고, 거래처가 바뀌면 이전·신규 거래처 잔액을 모두 다시 계산한다.
- 수정은 기존·신규 allocation 묶음 합집합을 ID 순으로 잠근 뒤 예약을 해제·재예약한다. 잠금 전에 읽은 값으로 새 스냅샷을 확정하지 않으며 기존 예약 해제 후의 최신 상태를 저장한다. 다른 전표 취소 또는 구조 변경이 먼저 잠갔으면 대기 후 그 변경을 반영해 검증한다. 새 예약 실패는 수정 전체를 rollback한다.
- 수정 실행의 예약 해제·재예약은 ORM 버전과 독립된 변경 식별자로 연결한다. 품목 규격·메모만 변경하거나 총액이 같은 배분 변경도 예약을 유지하며, Mutation replay는 재고 이동 이력을 중복 추가하지 않는다. 수정 API 재호출 자체는 새로운 편집으로 처리한다.
- `출고 완료`, `출하 완료`로 상태 변경될 때만 실제 난 묶음 `quantity`를 차감한다.
- 일반 판매 상태는 `작성중 → 출고 완료|취소`, 경매 판매 상태는 `작성중 → 출하 완료|취소`만 허용한다. 생성 시 `취소` 또는 판매 유형에 맞지 않는 완료 상태를 받을 수 없다.
- 판매 전표 취소는 삭제가 아니라 `salesStatus=취소` 상태 변경으로 처리한다.
- `작성중` 취소는 예약만 해제하고, 완료 전표 취소는 실제 차감 수량을 복구한다.
- 입금 이력이 있는 일반 판매 전표는 취소할 수 없다.
- 전표 응답의 `availableActions`는 현재 상태뿐 아니라 입금 이력과 경매 결과·정산 연결을 반영한 서버 판정값이다. 화면은 상태 문자열을 다시 조합하지 않고 이 값을 사용하되, 실제 변경 요청은 서버에서 재검증한다.
- 판매 전표 출력 API는 데이터를 변경하지 않고 A5 출력 화면에 필요한 조회 데이터만 제공한다.
- 브라우저 인쇄 CSS와 A5 레이아웃 렌더링은 프론트엔드 책임이다.
- 판매 상태 변경 API는 `PATCH /api/sales-slips/{salesSlipId}/sales-status`다.

## 8. 경매 출하 전표

- `salesType=AUCTION`인 판매 전표는 경매장 거래처를 기준으로 생성한다.
- 경매 판매는 `작성중`으로 저장 가능하고, `출하 완료` 시 shipment, lot가 생성된다.
- lot별 품목은 출하 수량과 0원 단가로 구성한다.
- 경매 판매 품목도 일반 판매와 같은 allocation 검증과 예약 규칙을 따른다.
- 일반 판매는 `salesType=DIRECT`이며 기존 요청처럼 유형을 생략해도 된다.
- 경매 판매전표 입금은 전표가 아니라 경매 정산에서 처리한다.
- 경매 시도·결과·상태 이력, 판매·반환 수량 또는 정산 연결이 있는 경매 전표는 취소할 수 없다. lot 상태를 `WAITING`으로 보정해도 이 기록은 보존한다. 취소 가능 여부와 실행은 같은 기준을 사용하며, 실행은 모든 lot를 ID 순서로 잠근 뒤 재검증한다. 처리 이력이 없는 대기 출하만 취소 시 shipment·lot를 제거하고 재고를 복구한다.

## 9. 출하·경매 추적

- 결과에 표기된 등급은 원본 결과와 lot 매칭 분석을 위한 값이며 출하 등급과 구별한다. 미입력 및 자동 생성 결과의 등급은 미상으로 유지하며 출하 등급으로 추정하지 않는다. 기존 결과와 Receipt는 보존한다.
- lot 목록은 서버 페이지네이션을 사용한다. `page`는 0부터 시작하고 `size`는 기본 20, 최대 100으로 본다.
- `reviewOnly`는 매칭 실패, 수량 불일치, 반환 추정 등 운영자 확인 대상 조회다.
- `returnOnly`는 반환 추정 대상, `waitingOnly`는 재경매 대기 lot 조회다.
- 요약 API는 페이지와 무관한 전체 데이터 집계다. 전체 lot 엔티티를 모두 적재하지 말고 DB 집계 쿼리를 우선한다.
- 반환 확인은 재경매 대기, 반환 추정, 부분 반환 상태에서만 가능하다는 정책이다.
- 낙찰 결과의 수량×단가가 현재 금액 저장 범위를 넘으면 결과 등록을 거절한다.
- 반환 확인 수량이 현재 확인 가능 수량보다 적으면 부분 반환, 같으면 반환 완료로 변경하고 상태 이력을 생성한다.
- 반환 수량을 생략하면 현재 확인 가능한 수량 전체를 처리한다.
- 결과 입력·반환 확인은 lot·업무 종류별 요청 identity를 갖는다. 같은 키·같은 입력은 완료 상태에서도 최초 저장 응답을 반환하며 수량·결과·상태 이력을 추가하지 않는다. 같은 키의 다른 입력은 `409 / AUCTION_REQUEST_KEY_CONFLICT`다. 실제 추가 경매·반환은 새 키를 사용한다.
- 비교는 바인딩된 입력 값 전체를 기준으로 한다. JSON 객체 속성 순서는 무관하며 생략된 선택 필드와 명시적 null은 같다. 문자열 값·결과 행 순서·자동 차수의 null/명시적 차수·반환 수량의 null/명시적 수량 변경은 다른 입력이다. 자동 차수와 생략한 반환 수량은 최초 실행에서만 결정한다.
- 최초 응답에는 저장된 이력 ID를 포함하고 당시의 lot 상태를 보존한다. 후속 업무가 있으면 replay 응답과 현재 상세는 다를 수 있다. lot 잠금·업무 변경·응답 receipt는 같은 트랜잭션에서 확정하며 실패한 요청은 키를 소비하지 않는다. 기존 identity 없는 결과·반환의 중복 여부는 자동 판정하지 않는다.
- 수량 보정 시 판매 + 대기 + 반환 수량은 출하 수량과 같아야 한다.
- 부분 반환·결과 반영·수량 보정은 상태가 같아도 판매·대기·반환 수량 전후값을 이력에 저장한다. V37 이전 이력의 수량은 미상이며 현재 값으로 복원하지 않는다. 상태와 수량이 모두 같은 요청은 이력을 추가하지 않는다.
- 직접 수량 보정은 경매 시도가 없고 반환 확인일도 없는 lot에만 허용한다. 결과·유찰·반환 추정·반환 확인 뒤 실제 수량 변경은 `409 / AUCTION_QUANTITY_ADJUSTMENT_LOCKED`로 거절한다. 수동 상태 변경으로 제한을 우회할 수 없고 정산·입금 스냅샷을 덮어쓰지 않는다. 기존 값 그대로의 보정 요청은 변경 없이 반환한다. 보상·결과 정정 이벤트 API는 후속 범위다.
- 보정 가능 여부는 lot 응답의 `quantityAdjustmentAllowed`로 제공한다. 과거 결과·반환 Receipt는 최초 스냅샷을 유지하며 신규 capability·수량 이력 필드가 미상일 수 있다. 현재 상태·가능 여부는 상세 조회로 확인한다.
- 상태 변경은 상태, 변경 사유, 작업자, 메모를 받고 상태 이력을 생성하는 성격이다.

## 10. 경매 정산

- 운영 목록은 서버 페이지를 사용하고 정산 결과 행은 단건 조회에서 받는다. 페이지와 합계는 같은 조회 조건을 적용하며 합계에는 페이지 제한을 적용하지 않는다. 호환용 전체 목록은 최신 500건까지만 반환한다.
- 경매 정산은 경매장과 경매일 조합으로 한 건만 생성한다.
- `amount > 0`인 경매 결과만 정산 행으로 연결한다.
- 정산 재구성 요청은 기존 행을 중복 생성하지 않아야 한다.
- 시작 시 초기화는 최대 결과 ID를 고정해 500건씩 대조하고 경매장·경매일 정산별로 commit한다. 실패한 정산은 rollback하며 앞서 commit한 정산은 유지한다. 재실행은 미연결 결과만 추가하고 기존 금융 snapshot·입금액을 보존한다. 실행 전체의 원자성이나 단일 DB snapshot을 보장하는 API로 취급하지 않는다.
- 현재 수수료와 공제액은 0원으로 본다.
- 예상 입금일은 거래처 정산 설정의 지연일과 달력일/영업일 계산 방식으로 정한다.

## 11. 거래처 정산 설정

- 거래처 관리 목록은 `GET /api/business-partners/page`의 서버 페이지네이션을 사용한다. `page`는 0부터 시작하고 `size`는 최대 100이다.
- 거래처 선택지는 서버 검색·페이지 조회를 사용한다. 전표 등록은 활성 거래처로 한정하고 판매 유형에 맞는 경매장 여부를 조회 조건에 반영한다. 목록 필터에서는 비활성 거래처도 조회한다. 선택된 비활성 거래처의 단건 조회는 과거 기록 표시용이며 신규 업무 사용을 허용하지 않는다.
- 기존 `GET /api/business-partners`는 이름·ID 순으로 활성 거래처 최대 500건을 반환하는 호환 경로다. 이름 검색과 유형 필터를 유지하며, 전체 거래처가 필요한 운영 화면에서 사용하지 않는다.
- 설정이 없으면 최초 조회 시 기본 설정을 생성한다.
- 경매장은 `AUCTION_DATE`, 다른 거래처는 `SALES_SLIP`이 기본 정산 단위다.
- 설정 응답의 capability는 현재 거래처 유형의 실제 정산 실행 지원 범위이며 저장한 정산 단위/자동 처리 선호값에서 추론하지 않는다. 현재 실행은 비경매 거래처의 전표별 수동 입금과 경매장의 경매일별 정산·수동 입금이다. 기존 `MONTHLY_BATCH`·자동 처리·선입금 선호값은 조회·수정 시 보존하지만 자동 실행을 활성화하지 않는다. 권한·과거 대상의 입금 가능 여부는 대상 업무의 action/검증을 따른다.
- 지연일과 달력일/영업일은 예상 입금일 계산에 적용한다. 자동 매칭·자동 정산·예치금·자동 차감과 규칙 JSON 실행은 지원하지 않는다. 새 묶음 정산·입금 분배는 별도 승인된 업무 모델/계약으로 다룬다.
- 입금자명 후보는 공백 제거 후 중복을 제거한다.
- `ruleJson`은 경매장별 결과 수신/파싱 규칙 확장용이며 현재 자동 수신 기능에서는 사용하지 않는다.

## 12. 수동 입금/입금 이벤트/잔액

- 운영 이력은 서버 페이지 조회를 사용한다. 이벤트 유형 조건은 페이지 조회 전에 적용하며 생략하면 모든 유형을 포함한다. 호환 전체 목록은 입금·연결 등을 합해 최신 500개 이벤트로 제한한다.
- 입금 확인은 `PAYMENT_RECEIVED`와 `MANUAL_MATCH_CONFIRMED` 이벤트를 함께 생성하는 정책이다.
- 수동 입금 요청에는 대상별 `idempotencyKey`가 필수다. 같은 키와 같은 금액·입금일 재요청은 기존 반영 결과를 반환하고 이벤트와 잔액을 중복 변경하지 않는다.
- 같은 대상의 멱등 키를 다른 금액 또는 입금일에 재사용하면 `409 / IDEMPOTENCY_KEY_REUSED`로 거부하며 대상·이벤트·잔액·감사를 변경하지 않는다. 필수 입력·형식·초과입금 등 기존 검증의 `400 / VALIDATION_ERROR`와 구분한다. 기존 입금 결과를 확인하고 실제 추가 입금에만 새 키를 사용한다.
- 판매 전표와 경매 정산 행을 잠근 상태에서 멱등성 확인과 입금 반영을 한 트랜잭션으로 처리한다.
- 잔액보다 작은 금액은 부분입금, 잔액과 같은 금액은 완납으로 처리한다.
- 잔액 초과 입금은 예치금 기능이 완전히 도입되기 전까지 거절한다.
- 예치금, 계좌 자동 매칭, 자동 정산, 입금 배분은 설계상 예정되어 있지만 OpenAPI에 없는 endpoint는 아직 구현으로 보지 않는다.
- 정산/입금 이력은 나중에 추적 가능해야 하므로 직접 삭제/수정보다 보정 이벤트를 우선한다.

## 13. 분석 집계

- 판매 분석은 `출고 완료`, `출하 완료` 상태 전표만 매출·출하·미입금 집계에 포함한다.
- 판매 분석 기간은 전표 `saleDate`를 기준으로 하며 최대 2년이다.
- 작업 분석은 `COMPLETED` 상태 작업의 `plannedStartDate`를 기준으로 집계한다.
- 판매 가능 수량은 `주의`, `이상`, `병해충`, `종료`, `폐기`, `판매 완료`, `생성 취소`가 아닌 난 묶음별 `quantity - reservedQuantity`를 합산한다.
- 조회 종료월 비교값은 같은 일수 범위의 직전 월 값이다.

## 경매 후속 결정과 실제 반환 도착

- 후속 결정은 유찰 잔량 전체에 하나의 방법을 적용한다. 농장 반환 결정만으로 재고를 생성하지 않는다.
- 실제 도착은 판매 API에서 새 묶음과 Farm 생성 Mutation을 함께 기록한다. 기존 입고 메뉴·InboundRecord와 연결하지 않는다.
- 유효한 도착이 있으면 결정 변경을 거절한다. 도착 취소 정정은 Farm 생성 보상과 Auction 수량 복구를 함께 처리하고 이력을 보존한다. 후속 사용으로 보상할 수 없으면 전체 정정을 `409 AUCTION_ARRIVAL_COMPENSATION_BLOCKED`로 거절한다.
- 경매장 처리는 결정 시 완료하며 Farm 수량을 바꾸지 않는다. 금액 환불과 실물 반환은 별개다.
- 새 결정·도착·취소 요청은 lot별 operation과 멱등 키로 최초 응답을 재사용한다. 같은 키의 입력 변경은 `409 AUCTION_REQUEST_KEY_CONFLICT`다.

경매 대금의 실제 수납액은 대상 거래처와 일치하는 유효 배분의 합계다. 자료 연결과 받을 금액이 확인되지 않은 대상은 새 입금을 받지 않는다. 과거 실제 입금의 대상 전환은 원래 입금·배분·부모 연결·멱등키를 보존하며, 지급 근거·지급액·확인을 추정하지 않는다. 전환된 정산의 기존 입금 경로는 성공한 원래 요청의 재전송만 허용한다.

일반 판매의 금액은 Direct의 거래·품목 가격과 Payment의 유효 배분에서 조회한다. 과거 금액·수납 대사나 현재 배분·거래처 참조에 검토가 남아 있으면 새 입금과 금액 수정을 차단한다. 상세의 서버 capability와 검토 필요 상태를 사용한다. 성공했던 원래 입금 키의 재전송은 중복 수납을 만들지 않고 조회할 수 있다. 이전 시점 대사 증거를 일상적인 수정으로 덮어쓰거나 자동 해소하지 않는다.
